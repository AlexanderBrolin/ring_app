### 0.3. ⛔ Находка против источника истины: колонка «в слайде» таблицы ADR-001 A15 неверна

A15 даёт дистанции, с которых голова цели попадает под ствол от бедра, и её слайд-колонка есть

| сборщик | 1.35 | 10.4 м | ~~5.2 м~~ | **13.4 м** |

| элита | 2.76 | 52.4 м | — | **34.3 м** |

## 1. Цель и границы

**Цель — игрок в любой момент видит линию, по которой уйдёт его выстрел.**

Две причины, обе подтверждены машиной:

1. **От бедра ствол горизонтален, и это скрыто от игрока целиком.** `ShotGeometry.Solve`,
   ветка `!AimHeld`: `vel3 = new float3(dir2 * weapon.ProjectileSpeed, 0f)` — снаряд рождается
   **строго горизонтально** на высоте дула (1.0 стоя, 0.45 в слайде), в 0.6 м впереди центра.
   Головы начинаются с 1.35 / 2.12 / 2.76 / 3.24 / 3.70, а ноги ганнера, элиты и Директора
   тянутся до 1.32 / 1.12 / 1.51 ⇒ **на высоте ствола этим трём всегда достаются ноги ×0.75**,
   а голова от бедра недостижима никому ближе 10.4 м (§0.3).
2. **Единственная сегодняшняя подсказка — круг на полу — про высоту молчит.** `CrosshairView.
   UpdateCone` рисует кольцо радиусом `tan(Spread.HipRadians(...)) × дистанция`: честно по
   **ширине** конуса, о высоте оси не говорит ничего. Это записано и в ADR-001 A15 («Высоту
   ствола круг не показывает вообще»).

⇒ **Жалоба владельца на вехе 10.09 — не про баг, а про невидимую геометрию.**

**В задачу входит:** луч включён всегда и ведёт за курсором (Н37); упор в первое тело или
геометрию арены (Н38); жёлтый от бедра, зонный в прицеле; удаление круга (Н41) **и точки на
полу от бедра** (Н45); **засечки разброса на конце луча** (Н46); прибор в дев-оверлее (Н42);
доки `app-sr83` и отмена PD15 (Н43); амендменты ADR (§9).

**Вне задачи:** вариант «б» целеуказателя (луч по рисунку — дверь на веху); фиксированная
длина «2/3 видимого радиуса» (Н37, веха); **ретикл под ФОРМУ рисунка** — засечки несут ширину
конуса, а не кривую, и **долг ADR-001 A15 остаётся отложенным** (§9 A16(б)); засечки в
**прицельном** режиме (вопрос вехи);
`app-94sk`, `app-ibak`, `app-u6xi`, `app-jjvh`; `app-umeg` (нужен прибор, урок 716);
`app-77s7`; `app-per9`.

### 3.2. Симуляция: линия огня как чистая функция

**Почему дом — `Ring.Simulation`.** Три довода:

1. **`HitZones` — `internal` по решению, записанному в его шапке.** Ходить по `Parts` из
   Presentation нельзя.
2. **Ответ обязан быть тем же, что даёт сервер.** Физический каст по прокси отвечает на другой
   вопрос; расхождение прокси и `Parts` — предмет `app-94sk`.
3. **Тестируемость.** `AimRayView` и `AimProvider` — `MonoBehaviour`, EditMode их не заводит.
   Прецедент «чистая функция из `Ring.Simulation`, которую читает Presentation» уже есть.

**Контракт.**

```csharp
public enum AimStop : byte { Range = 0, Barrier = 1, RingWall = 2, Body = 3 }

public readonly struct AimLineSolution
{
    public readonly float2 Start;          // дуло в плане
    public readonly float2 Dir;            // единичное направление линии
    public readonly float Length;          // до упора
    public readonly float Height;          // постоянная высота линии = высота дула
    public readonly AimStop Stop;
    public readonly HitZone Zone;          // часть тела под осью; None вне Body
    public readonly float NotchDistance;   // где стоят засечки (§3.6)
    public readonly float NotchHalfWidth;  // полуширина конуса на этой дистанции

    public float2 End     => Start + Dir * Length;
    public float2 NotchAt => Start + Dir * NotchDistance;
}

public static float2 MuzzlePlan(float2 heroPos, float2 aimPoint, float muzzleOffset,
                                out float2 dir);

public static AimLineSolution Solve(float2 heroPos, float2 aimPoint, float muzzleHeight,
                                    in SimConfig cfg, RenderSnapshot snap, int selfIndex);

public static void Notches(in AimLineSolution line, float strokeLength,
                           out float2 a0, out float2 a1, out float2 b0, out float2 b1);
```

⚠ **У каждого поля есть читатель** (Ruling 73): `End`/`Height` — луч; `Start`/`Dir`/`NotchAt`/
`NotchHalfWidth` — засечки; `Length`/`Stop`/`Zone` — прибор §3.8. Индекс задетого тела **не
объявляется**: читателя нет.
⚠ **`End` и `NotchAt` — свойства, а не поля** (рулинг 291): одно число — один дом.

**Порядок кандидатов — форма снаряда, повторённая, а не пересказанная.**

1. **Барьеры и обод — одним вызовом `ProjectileFlight.Step`** над синтетическим раундом:
   ```csharp
   var probe = new ProjectileState {
       Pos = start, Vel = dir * reach, Height = muzzleHeight, VelZ = 0f,
       Radius = cfg.Weapon.ProjectileRadius };
   ProjectileFlight.StepResult step = ProjectileFlight.Step(in probe, in cfg, dt: 1f);
   ```
   ⭐⭐ **Так решено вместо собственной перегрузки `BarrierStops`, и причина измерена:** прецедент
   вызова этой пары **из чужой сборки с собранным вручную `ProjectileState`** уже есть
   (`TracerProjectiles`), а перегрузка «по паре высот» была бы **неполной** — существующий член
   читает ещё и `p.Radius`, а он у снаряда моба (0.15 в фикстуре) не равен оружейному (0.12).
   При `VelZ = 0` напольный кандидат `Step` не срабатывает по построению.
2. **Высотный гейт барьера — существующим членом, под тем же гейтом, что у прецедента:**
   `step.HasBarrier && ProjectileFlight.BarrierStops(in probe, in cfg, muzzleHeight, 1f)`.
   При `BarrierTop <= 0` он отвечает `true`; при отгруженных 3.0 и высоте ствола 1.0 / 0.45 —
   тоже `true`. ⛔ **Но спрашивается он всё равно:** ответ по числу перестанет быть верным, если
   число тронут.
   ⭐ **Одного барьерного кандидата достаточно, и это довод, а не экономия:** у всех внутренних
   барьеров один общий верх, а линия горизонтальна ⇒ если ближний барьер не держит, не держит ни
   один. Это довод монотонности `ProjectileFlight`, у горизонтали вырожденный в равенство.
3. **Обод** — `step.HasRingWall` / `step.RingWallT`. ⚠ У обода **нет модельного верха** намеренно
   (решение владельца 2026-08-11), гейта здесь нет и быть не должно.
4. **Тела — ДВЕ ступени, как у снаряда:**
   **(а) широкая фаза** — `Geometry.SegmentCircle(start, end, ProjectileRadius, bodyPos,
   bodyRadius, out t)` по **радиусу тела** (`SimConfig.MobConfigFor(in cfg, type).Radius` для
   мобов, `cfg.Hero.Radius` для сборщиков);
   **(б) мин-скан и уточнение победителя** — `HitZones.Resolve(parts, start, end,
   ProjectileRadius, bodyPos, hStart: h, hEnd: h, overlapTop, out zone, out _, out _, out tPart)`;
   отказ исключает кандидата и **скан повторяется**.
   `overlapTop` — `HitZones.StackTop(parts)` для стоящего и **`Hero.SlideProfileTop`** для
   слайдящего сборщика: тот же выбор, что делает `ProjectileSystem`. ⚠ Бит слайда чужого
   сборщика **едет по проводу**, поэтому правило работает и в PvP.
   ⛔ **Одной ступени мало:** части соосны и не шире тела ⇒ `t` части всегда не меньше `t` круга,
   и зазор тем больше, чем ближе линия к касательной. Ранжируя по частям, мы получили бы другой
   порядок, чем у снаряда — а вся ценность в том, что порядок **тот же**.
5. **Предел дальности** — `ProjectileSpeed × ProjectileLifetime` (**78.75 м**; фикстура 52.5 м).
   Столько живёт снаряд; новой ручки не заводится.

Победитель — **минимум по `t`**; при точном равенстве выигрывает спрошенный раньше (строгое `<`)
— та же дисциплина, что у `SweepArena`, и она пиньется тестом.

**Кого линия видит — на двух бэкендах это разный набор:**

- **Сетевой:** кадр несёт только тела, прошедшие серверный фильтр (CR 4) ⇒ дальше `SightRadius
  45` и за стенами линия в тело не упрётся.
- **Локальный (редактор, оффлайн):** фога нет **вообще** — кадр несёт всех мобов и весь ростер.
  ⛔ **Утечки нет ни там, ни там:** оффлайн эти тела **и нарисованы**, а на сети их в кадре нет.
- **Мобы гейта не требуют:** массив живой по построению (`DamageMob` выметает мёртвого
  swap-remove'ом). ⛔ **Гейт по `Hp <= 0` был бы прямым дефектом:** `Hp` на проводе квантуется в
  байт, и живое тело с `Hp/MaxHp < 1/510` декодируется в ноль — у Директора это **последние
  4.9 HP**, то есть указатель врал бы ровно в момент добивания босса.
- **Сборщики — по `Alive`**, тем же правилом, каким их гейтит снаряд. ⚠ Это **не** `Hp > 0`:
  эвакуировавшийся уходит с `Alive = false` при положительном здоровье. ⚠ Слот, про который кадр
  ничего не сказал, читается как `default(PlayerState)` — не жив; `Alive` отсекает его по
  правилу, а не по совпадению.
- **Своё тело исключается по `selfIndex`** = `snap.LocalPlayerIndex`. ⚠ В `AimProvider` тот же
  вопрос решается флагом `IsLocal` на кукле — механизм другой, вопрос один.

**Чего линия НЕ делает:**

- **Не рисует рикошет** (ADR-002 A26(в): ошибка направления после отскока — до 14.1°).
- **Не учитывает пробитие** (`PierceMassRatio 0.06` — не пробивается никто).
- **Не воспроизводит предшаг и рисунок.** Настоящий снаряд рождается вдоль направления **после**
  разброса и на `overshoot × horizSpeed` дальше по линии (до **1.75 м**). Линия — **ось до
  розыгрыша**, и в этом её смысл.
- **Не отматывает.** ⭐ Пара, которую она строит, — **судейская**: `RenderCurr.Player` несёт
  предсказанное состояние клиента, чужие тела — интерполированную картинку, то есть ровно
  сочетание A24(г). ⚠ **А цена — проектная и больше сетевой:** линия честна про **направление** и
  молчит про **упреждение** (0.38 с полёта на 20 м; ADR-001 §9 — «упреждение — скилл»); поверх
  лежит остаток лаг-компенсации **0.73–1.05 м**.
  ⚠ И ещё полтика: чужие тела **рисуются** интерполяцией между `RenderPrev` и `RenderCurr`, а
  линия решается по `RenderCurr` ⇒ упор стоит на теле, нарисованном чуть позади. На вехе это
  читается как «луч чуть впереди моба», и это не дефект упора.
- **Ничего не пишет.**

**Цена по кадру — числом.** Широкая фаза — один `SegmentCircle` (около двадцати операций) на
тело; худший случай оффлайн — `MaxMobs 1350`, порядка 27 тысяч операций за кадр, и
`HitZones.Resolve` зовётся **один раз**, для победителя. Аллокаций ноль.

### 3.3. Presentation: луч от бедра

**`AimProvider`** — решение линии кэшируется рядом с остальными значениями кадра:

```csharp
_cachedHipLine = AimLine.Solve(_runner.RenderCurr.Player.Pos, planeAimSimPos,
                               _runner.RenderMuzzleHeight, _runner.Config,
                               _runner.RenderCurr, _runner.RenderCurr.LocalPlayerIndex);
```

⛔⛔ **Считается КАЖДЫЙ кадр, в ОБЕИХ ветках, под тем же гейтом `Ready`, что и всё остальное в
этом классе.** v3 писала «только в бедровой ветке и только при `AimActive`» — и это был дефект,
найденный кругом 2: кэш стал бы **произвольно старым**. Отпустил ПКМ после пяти секунд
прицеливания — первый бедровый кадр нарисовал бы линию пятисекундной давности; после паузы,
смерти или рестарта — линию **из прошлого матча**. Сосед по классу (`CurrentImpactWorldPoint`)
пишется в обеих ветках именно поэтому, и аналогия v3 на него ссылалась, не проверив.
⇒ **Правило одно: пишем всегда, рисуем по `AimActive`.** Цена названа: один проход по видимым
телам в кадре, включая паузу и экран смерти (порядка 27 тысяч операций в худшем случае).
⚠ **Гейт `AimActive` оборачивает только рисование в `AimRayView`**, а не метод провайдера:
ранний возврат из `LateUpdate` убил бы обновление прицельных значений и маркера.

⚠ **Аим — кадровый**, тот же `planeAimSimPos`, что читал маркер («no tick quantization»).
⚠ **Позиция сборщика — из `RenderCurr`**, и это **предсказанное место этого клиента** (не
«последний полный тик»: в пару копируется весь предсказанный `PlayerState`, интерполируется
только позиция). Берётся оно потому, что от него же считается дуло и его же читает
`ResolveImpactWorldPoint` — операнды из одной фазы (694).
⚠ **Кэш — один раз за кадр** (K15), и **вид читает значение прошлого кадра**: `AimProvider`
исполняется позже вида. Это тот же контракт, по которому уже живёт `CurrentImpactWorldPoint`.

**`AimRayView`** — **пять** правок:

1. **Гейт `AimHeld` снимается.** Гейт `AimActive` **остаётся**.
2. **Начало — сокет куклы** (Н40).
3. **Конец — из провайдера:** в прицеле `CurrentImpactWorldPoint` (без изменений), от бедра —
   `SimSpace.ToWorld(line.End) + Vector3.up * line.Height`.
   ⛔ **От бедра нельзя брать `CurrentImpactWorldPoint`:** он считается по курсору и режется полом,
   то есть отвечает на вопрос прицельного режима; получился бы луч, **ныряющий из дула в пол**.
4. **Цвет** — §3.4.
5. **Засечки** — §3.6: вид зовёт `AimLine.Notches`, ставит четыре точки и **сам не решает ничего**.

⚠ **Слайд едет сам собой:** `RenderMuzzleHeight` — единственный дом тернара **в Presentation**
(тот же тернар живёт в `ShotGeometry.Solve`, и это названная копия, а не находка).

**⚠ Рывок картинки на переходе бедро↔прицел — назван, а не обнаружен на вехе.** Нажатие ПКМ
меняет за один кадр четыре вещи: конец луча (упор до 78.75 м → точка курсора), цвет
(жёлтый → зонный), появление маркера и исчезновение засечек. На цели в восьми метрах это
десятикратное изменение длины. Пункт вехи заведён.

**⚠ Дэш: луч горит, а выстрела не будет.** `CanFireWhileDash 0`, и `AimActive` дэша не исключает.
⇒ **Луч в дэше не гасится**, довод — длительность: 0.09 с = три кадра при 30 Гц; мигание
читалось бы как дефект картинки. Прецедент обратного решения (рюкзак в `AimActive`) отличается
сроком. Пункт вехи заведён.

### 3.4. Цвет

- **От бедра — жёлтый** (Н37), одним цветом, без зон; число — `GameFeelConfig.AimRayHipColor`.
- **В прицеле — как сегодня:** зонная окраска плюс яркостный буст на голове.
- Применение — `MaterialPropertyBlock`, без материалов на экземпляр.
- ⛔⛔ **Засечки НЕ получают цвет и ширину «за компанию» с лучом, и это находка круга 2.** Цвет
  луча живёт **не в материале**, а в per-renderer блоке; ширина — в `startWidth`/`endWidth` того
  же рендерера. Общий `sharedMaterial` дал бы засечкам **запечённый циан** и дефолтную толщину.
  ⇒ Тот же блок и та же ширина применяются **к каждому** из трёх рендереров явно.
- ⚠ `AimRayAlpha` масштабирует **яркость эмиссии**, а не прозрачность.
- ⚠ **У цвета луча два дома** (базовый прицельный — в материале, бедровый — в SO), и заход их не
  сводит: это правка чужого решения ради симметрии, не нужная ни одному пункту вехи.

### 3.5. Круг конуса и точка на полу уходят (Н41, Н45)

**Что уходит из `CrosshairView`:** поле `_cone`, метод `UpdateCone`, буфер `_conePoints`,
константа `ConeSegments`, обе ветки `_cone.enabled`.

⭐ **И весь блок маркера уходит под `aimHeld`** (Н45). ⛔ **Гасить одну ветку мало, и это находка
круга 2:** позиционирование диска стоит в ветке `!aimHeld`, но **масштаб** и **цвет** пишутся на
обеих, а эджевая логика звукового тика читает зону каждый кадр. Оставь их — и невидимый диск
продолжит получать записи тридцать раз в секунду, ровно против довода, ради которого ветку и
снимают. ⇒ Под `aimHeld` уходит **весь блок** от чтения точки до `SetPropertyBlock`; наружу
остаются `UpdateCursor()` и `_markerRenderer.enabled = aimHeld`.
⚠ **Порядок строк:** сегодня включение рендерера стоит **выше** объявления `aimHeld` — либо
поднимается объявление, либо строка переезжает.
⚠ **В прицеле маркер остаётся** — точка прицела, зонная окраска, пульс, звуковой тик.
⇒ **От бедра `CrosshairView` не рисует ничего**, и роль класса сужается до двух: владелец
OS-курсора (записанное решение владельца — единственный писатель `Cursor.visible` в проекте) и
прицельный маркер. Это пишется в его шапку.
⚠ **И дока класса станет ложной в другом месте:** «радиус конуса — единственное место, где класс
читает снимок» — после правки класс не читает ни снимок, ни `Config` вовсе; `using` под `Spread`
становится мёртвым.

**Бутстрап.** Объект `Crosshair/SpreadCone` создаётся бутстрапом; удаление — **идемпотентно**.
⛔ **Вместе с объектом снимаются строка, создающая его материал, и константа его имени.**
⚠ **Сам `.mat` остаётся на диске:** механизм A27 (сиротские ключи, которые вычистит ближайшая
перезапись) сюда **не переносится** — там у ключей не было писателя, здесь писатель есть.

**⛔ ЦЕНА УДАЛЕНИЯ БЫЛА НАЗВАНА И ЗАКРЫТА РЕШЕНИЕМ ВЛАДЕЛЬЦА.** Круг показывал, как конус
**растёт**: бег ×1.5, слайд ×2, накопленная отдача. Луч этого не показывает — он рисует ось и
выглядит одинаково стоя, на бегу и в слайде. Без замены из игры ушёл бы единственный индикатор
правила ADR-001 A1(а) и будущей прокачки «разброс снижается» (ADR-002 A19). ⇒ **Заменой стали
засечки (Н46, §3.6).**

**Следствие для видимости.** `Spread` и `SprayPattern` были `public` **под названного
потребителя** — `CrosshairView`. ⛔ **Понижается `Spread` ЦЕЛИКОМ, а не один член:** его шапка
запрещает раскалывать один конус по двум уровням доступа. `SprayPattern` — так же.
⚠ **Засечки этого не отменяют:** полуширину считает **новый член самого `Spread`**, и зовут его
изнутри той же сборки (§3.6). Внешнего читателя у конуса не остаётся — проверено свипом.
⚠ **`ShotGeometry` остаётся `public`:** `ShotSolution` читается из `Ring.Presentation.Net`, а
раскалывать тип и его фабрику по уровням доступа запрещает та же дока. Но её шапка обосновывает
публичность **исчезающим ретиклом** и правится вместе с прочими (§3.10).
⚠ **Тесты не задеты:** `InternalsVisibleTo` на `Ring.Simulation.Tests` уже стоит.

### 3.6. Засечки разброса (Н46)

**Что рисуется.** На линии — **два коротких поперечных штриха**, отстоящих от оси на полуширину
конуса, по одному в каждую сторону. До открытия огня они почти сходятся, в очереди расходятся,
на бегу — в полтора раза шире, в слайде — вдвое.

**⛔ Где они стоят — и это ГЛАВНАЯ правка круга 2.** v3 ставила их на **конце луча**, и это
ломало индикатор ровно там, где он нужен: при пустой линии конец — предел дальности 78.75 м, а
полуширина там **7.58 м** стоя и **15.31 м** в слайде при видимой полосе земли около **25 м**,
то есть засечек на экране нет вовсе. Хуже: соскальзывание мыши с моба (упор 9 м) на пустоту
двигало бы зазор **в 8.75 раза за кадр** — одна картинка кодировала бы и угол конуса, и
случайную дистанцию упора.
⇒ **Засечки стоят на `NotchDistance = min(Length, дистанция до курсора)`**, и полуширина
считается **на ней же**. Круг делал ровно это: он считался `tan(HipRadians) × distance(игрок,
курсор)`. Тогда засечки всегда на экране, не скачут, а при упоре в стену раньше курсора стоят на
стене.
⭐ **Побочно это возвращает указатель.** После Н45 от бедра на экране нет ни точки, ни круга, а
OS-курсор скрыт весь бой; луч же через экранную точку мыши **не проходит** — ствол на 1.0 м
проецируется при наклоне камеры 55° на **0.70 м** земной дистанции «вверх по экрану» (в слайде
0.32). Пара засечек, стоящая на дистанции курсора, становится тем якорем, которого иначе нет.
⚠ Цена этого якоря названа: он смещён вверх по экрану на те же 0.70 м и с мышью не совпадает.

**Формула не заводится заново — она переезжает,** и переезжает **в дом конуса**:

```csharp
// Spread (internal, рядом с HipRadians и AimRadians)
internal static float HipHalfWidth(in WeaponSimConfig weapon, in PlayerState p,
                                   in HeroSimConfig hero, float distance);
```

⛔ **Дом выбран по находке круга 2:** три операнда этой функции — ровно операнды
`Spread.HipRadians`, а шапка `Spread` объявлена «единственным домом конуса». Класть ширину конуса
в файл «линии огня» значило бы завести конусу третий дом — против того самого правила, на
которое опирается §3.5.
⚠ **`AimLine.Solve` зовёт её и кладёт ответ в `NotchHalfWidth`** — место вызова пиньется тестом,
а не остаётся выбором вида.

⛔⛔ **Кламп обязателен, и это не перестраховка.** Слайдеры владельца дают конус до **10 рад**
(§0.1), а `tan` на `π/2` уходит в бесконечность и меняет знак. Полуширина клампится по углу и не
может быть отрицательной или неконечной. У соседа этот инвариант записан прямо («never NaN»), и
здесь он пиньется тестом.

**Геометрия штриха — тоже чистая функция, а не решение вида** (`AimLine.Notches`): перпендикуляр
к направлению **линии**, центр каждого штриха на `NotchAt ± perp × NotchHalfWidth`, длина
`strokeLength` вдоль перпендикуляра. ⛔ Без этого в `MonoBehaviour` осели бы четыре решения
(перпендикуляр, якорь, высота, концы), у которых нет ни теста, ни мутации.

**Длина штриха — не абсолют,** и это находка круга 2: полный зазор между засечками **до открытия
огня** на десяти метрах равен 0.52 м, и штрих в 0.35 м слил бы пару в одну метку ровно тогда,
когда решение и принимается — до первого выстрела. ⇒ Длина = **доля полуширины с метровым
полом**: `strokeLength = max(AimRayNotchMinLength, AimRayNotchFrac × NotchHalfWidth)`, стартово
`Frac 0.5`, `MinLength 0.08`.

**Где живут и как гаснут.** Два чайлд-объекта под `AimRay`, каждый со своим `LineRenderer` на две
точки, создаются бутстрапом идемпотентно, проводятся ссылками (`SetRef` — так проведён и конус) и
делят **материал** луча, получая цвет и ширину **своим** блоком (§3.4).
⛔⛔ **У них СВОЙ выключатель, и это находка круга 2:** засечки — отдельные объекты, и
`enabled = false` на рендерере луча их не касается. Оставь как есть — и они переживут прицельный
режим, паузу, экран смерти, рюкзак, кадры без куклы и переедут в следующий матч. ⇒ Правило одно и
стоит на **всех** путях вида: `notch.enabled = луч рисуется && !aimHeld && strokeLength > 0`.
⭐ **Гашение исполняется выключателем, а не нулевой длиной:** `LineRenderer` с двумя совпавшими
точками рисует вырожденный квад, а не пустоту.
⛔ **Одним `LineRenderer` два раздельных штриха не нарисовать** — он рисует одну ломаную, а трюк
с нулевой шириной в узлах держится на кривой ширины, которую следующий правщик снимет не заметив.
⚠ **Бутстрапу нужен хелпер, а не третья копия:** блок «найти-или-создать чайлд → get-or-add
`LineRenderer` с одноразовыми настройками → self-heal материала» уже стоит в файле **дважды**
посимвольно одинаково, а с засечками стал бы **четырежды**. ⇒ `EditorBootstrapUtils.
EnsureWorldLine(...)` по образцу `GetOrCreateMaterial`/`EnsureVisual`, и все места переводятся на
него. ⚠ Сцена, забутстрапленная **до** этой задачи, чайлдов не имеет — вид обязан переживать
несвязанные ссылки, как это уже делает `MuzzleFlashView` с сокетом.

**Только от бедра.** В прицеле картинка остаётся сегодняшней (Н37): там своя точка прицела и свой
конус — ⚠ **потолок которого 5.50°, а не 4.01°** (4.01° — это только слагаемое отдачи; дока
`Spread` говорит это дословно). Нужны ли засечки в прицеле — вопрос вехи.

⚠ **Цена названа трижды:**
1. Засечки показывают **половину ширины конуса**, то есть границу, а не место попадания; и
   огибающая читается как «равновероятно между штрихами», хотя две трети угла детерминированы
   (`SprayVariance 0.35`). У круга был тот же порок.
   ⚠ И ещё одно прочтение, которого у круга не было: стоя **на теле** пара штрихов читается как
   бракет «цель захвачена» — на ганнере в девяти метрах они встают на 0.37 м снаружи силуэта, на
   высоте его **ног**.
2. Они молчат про **вертикаль** рисунка (её в топ-дауне не видно — решение Н29) и про
   **упреждение** (0.38 с полёта на 20 м).
3. Ракурс сжимает поперечную ось в `sin 55° = 0.82` — та же цена была у круга, который рисовался
   эллипсом; это не регресс, но на вехе может читаться как дефект.

⚠ **Вырожденные случаи названы:** при нулевой полуширине два штриха ложатся друг на друга и дают
**одну поперечную чёрточку**, а не пустоту (гасить — выключателем); при нулевой длине линии (дуло
внутри круга) луч и засечки схлопываются у дула — §4.4 тест 18 пинит выбранное поведение, а веха
его показывает.

### 3.7. Живая правка чисел на вехе

Поведение двух бэкендов **разное**, и веха идёт на сетевом:

- **Локальный** применяет правку в месте, и луч отреагирует сам — он читает `Config` каждый кадр.
- **Сетевой `ApplyConfig` игнорирует** (балансные числа на клиенте — серверные, хеш рукопожатия
  посчитан от них), причём флаг «конфиг тронут» взводится всё равно. ⇒ **На стенде владелец
  покрутит `AimRayHipColor`, `AimRayNotchFrac` и `AimRayNotchMinLength` и увидит эффект
  мгновенно** (это `GameFeelConfig`, он не серверный), **а `MuzzleHeight`, `ProjectileLifetime`,
  `ProjectileSpeed`, `SpreadRad` и `BarrierTop` не двинут ни длину луча, ни ширину засечек.**
- ⚠ Смена топологии арены на локальном бэкенде роняет `Ready` на кадр, и провайдер оставляет кэш
  прежним вместо броска; наружу это не течёт, потому что рисование гейтится `AimActive`.

### 4.4. Тесты (24 фикстуры `AimLineTests` + 4 в `WeaponTests` + строка в `AllocationTests`)

14. ⭐ **Гейт сборщиков — `Alive`:** сборщик с `Alive == false` и **положительным `Hp`**
    (эвакуация) линию не останавливает; живой моб с `Hp`, квантованным в ноль, — останавливает.
15. **Зона под стволом:** ганнер в пяти метрах — `Legs`; сборщик в пяти метрах — `Body`.
16. **Курсор ближе дула:** направление не переворачивается.
17. **Вырожденный ввод:** курсор в позиции сборщика ⇒ фолбэк, ни `NaN`, ни нуля.
18. ⭐ **Дуло внутри круга:** поведение пиньется явно (линия не схлопывается молча).
19. ⭐⭐ **Порядок — по кругу тела, а не по части:** тело A задето по касательной и ближе, тело B
    в лоб и дальше; `t` круга A меньше, `t` части A больше. Двухступенчатый порядок выбирает **A**.

**Засечки (`AimLineTests`, кроме 20–23):**

20. **Полуширина делегирует конусу** (`WeaponTests`): `HipHalfWidth(w,p,h,d) ==
    tan(HipRadians(w,p,h)) × d` для стоящего, бегущего и слайдящего состояния. ⛔ **Именно так, а
    не «отношение равно множителю»:** `tan` нелинеен, и на фикстуре отношение полуширин равно
    **1.500423** и **2.001354** — строгий ассерт на 1.5 и 2.0 покраснел бы на верном коде.
    ⚠ Порог бега — `>=`, поэтому фикстура ставит скорость **ровно** на порог.
21. **Полуширина линейна по дистанции** (`WeaponTests`): удвоение дистанции удваивает полуширину.
22. **Отдача входит в полуширину** (`WeaponTests`): премисса — свойствами (`RecoilPerShotRad`
    против `RecoilRecoveryRadPerSec × FireInterval`), а не литералом.
23. ⭐ **Кламп** (`WeaponTests`): при конусе из крайних значений слайдеров полуширина **конечна и
    неотрицательна**.
24. ⭐⭐ **`NotchDistance == min(Length, дистанция до курсора)`:** курсор ближе упора — засечки у
    курсора; упор ближе курсора (стена в трёх метрах) — засечки на стене.
25. ⭐ **Штрихи стоят на границах конуса:** расстояние каждого от оси равно `NotchHalfWidth`, оба
    перпендикулярны **направлению линии**.
26. **Длина штриха:** `max(MinLength, Frac × NotchHalfWidth)` — на малой полуширине работает пол,
    на большой — доля.

**Швы:**

27. **Ноль аллокаций** — строка в `AllocationTests` на насыщенном мире; покрывает `Solve` и
    `Notches`. ⚠ Риск вида (`SetPosition` по точкам, **не** `SetPositions(new Vector3[2])`)
    EditMode недостижим и назван в §3.6; ⚠ и образец кэшированного буфера этой же задачей
    удаляется вместе с конусом.
28. ⭐⭐ **Один ответ на двоих:** в фикстурном мире с занулёнными
    `SpreadRad`/`RecoilMaxRad`/`SprayVariance`/`SprayPitchAmplitude` выстрел от бедра приходит
    туда, куда показала линия: точка попадания и зона из события совпадают с `End`/`Zone`.
    ⚠ Серверная сторона читается **из события**. ⚠ Премиссы: `overshoot == 0`; сравнение — по
    **телу и зоне**, а по точке — с допуском шага снаряда фикстуры (1.167 м).
29. ⭐ **Дуло картинки совпадает с дулом выстрела:** `MuzzlePlan` против `SpawnPos` решения
    выстрела при `overshoot == 0` и нулевом конусе — свидетель того, что вторая копия формулы
    дула в `ShotGeometry.Solve` не разошлась.

⚠ **Счёт:** 29 пунктов. Пункты 20–23 живут в **`WeaponTests`**, рядом с
`HipSpread_RunAndSlideMultipliers`, который уже пинит множители и порог; пункт 27 — в
`AllocationTests`; остальные **24** — фикстуры `AimLineTests`.
⚠ Тесты 20–23 формулу заново не переписывают: сосед доказывает **множители**, новые —
**делегирование, дистанцию и кламп**.

## 5. Веха: плейтест владельца

**Условие — CR 7:** дев-сервер `80/5`, клиенты `-ring-latency off`, `-logFile` с уникальным
именем. Стенд — только по слову владельца.

1. ⭐⭐ **Луч виден всегда и ведёт за курсором** (Н37).
2. ⭐⭐ **Стало понятно, почему урон приходит не туда:** видно, что ствол проходит под головой
   ганнера, элиты и Директора.
3. ⭐ **Упор читается:** тело, стена, обод; не мешает ли дёрганье конца в толпе.
4. **Луч растёт из ствола модели** (Н40), прибор показывает `Δ` (0.6…1.05 м; наклон до 5.1° на
   пяти метрах в слайде).
5. **Жёлтый от бедра, зонный в прицеле** — не путается ли; ⚠ **и засечки того же цвета, что луч**,
   а не циановые (жертва мутации §4.3).
6. **Луч гаснет там, где игра прицела не просит:** пауза, экран смерти, рюкзак — ⚠ **и засечки
   гаснут вместе с ним**. ⚠ **И не гаснет в дэше** (90 мс) — врёт ли это.
7. ⭐⭐ **Засечки работают как замена кругу (Н46):** видно ли по ним, что бег и слайд ухудшают
   кучность, и что очередь разводит отдача. ⚠ Числа: полуширина на десяти метрах — **0.26 м до
   огня**, **0.96 м** в очереди стоя, **1.45** на бегу, **1.94** в слайде.
8. **Слайд:** луч опускается до 0.45.
9. **Прибор:** строка `AimRay`. ⚠ **Ожидаемый сюрприз назван заранее:** на сетевом стенде живьём
   крутятся только `GameFeelConfig`-числа (цвет и засечки); высота, длина и барьер — серверные.
10. 🆕 **Длина при пустой линии:** 78.75 м против «2/3 видимого радиуса» = 30 м. ⚠ Видно около
    25 м, поэтому различие проявится вблизи упоров.
11. **Не мешает ли луч в бою:** не перекрывает ли картинку, не рябит ли на спрее, не спорит ли с
    трассером, **читается ли вспышка попадания** при постоянно горящей эмиссии (ADR-001 §10).
12. 🆕 **Засечки только от бедра — так и надо?** В прицеле их нет намеренно; конус там тоже есть
    (потолок 5.50°).
13. 🆕 ⭐⭐ **Где мышь?** Точки на полу нет (Н45), OS-курсор скрыт, а луч через экранную точку
    курсора **не проходит** — он идёт на 0.70 м «выше» неё (в слайде 0.32); якорем работает пара
    засечек, стоящая на дистанции курсора. Проведи мышью по краю моба и скажи, находится ли мышь.
    ⚠ Возврат точки — одна строка.
14. 🆕 **Длина засечки** (`Frac 0.5`, пол 0.08 м): не крупные ли, не мелкие ли; ⚠ **и нет ли между
    штрихами соединяющего отрезка** (жертва мутации §4.3).
15. 🆕 **Переход бедро↔прицел:** не рвёт ли картинку — конец луча прыгает с упора на точку
    курсора, меняется цвет, появляется маркер, исчезают засечки.

⚠ **PvP-пункты `app-per9` соло-забегом не закрываются.**

## 9. Амендменты ADR (нумерация — по документам, не сквозная)

⚠ Последние на сегодня: ADR-001 — **A15**, ADR-002 — **A29**, ADR-003 — **A8**.

1. **ADR-001 A16**, тремя пунктами:
   - **(а)** уточняет **A1(а)**: слова «ретикл — круг на полу» снимаются. От бедра ретикла-круга

     разброса на нём** (Н46), которые несут ту же ширину конуса, что несло кольцо: они растут от

     (Н45). ⛔ **Записать надо и отступление от жанровой нормы:** индикатор разброса обычно живёт
     отдельным ретиклом в экранном пространстве, а здесь сращён с лучом в мировом — решение
     владельца, и цена его в §3.6.

     ФОРМУ рисунка» с условием «отдельной задачей **после плейтеста, когда числа рисунка

     не показывают и **наследуют тот самый дефект**, ради которого долг заведён: симметричная
     фигура вокруг знакопеременной кривой о следующем выстреле не говорит. ⚠ Ведущая ось рисунка
     — **горизонталь** (амплитуда 1.0 против 0.35), и теряется именно она.

     указатель высоты ствола» — да, и это луч.
     ⚠ **Запись фиксирует механизм, а не вердикт вехи** (прецедент — ADR-002 A29): амендменты
     пишутся до плейтеста, и если владелец от луча или засечек откажется, это правится вторым
