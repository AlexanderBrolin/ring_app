## 1. Цель и границы

**Цель — вернуть волнам темп.** Сегодня темпа нет вовсе: следующая волна
ставится в очередь единственным путём — полным вайпом **всей арены**
(`WaveSystem.cs:74`, `wave.PendingTotal == 0 && w.MobCount == 0`), и
`WavePause` начинает тикать только там (`:56-60`). Носитель бежит 7.5 м/с
против 4–5.2 у мобов, уходит от единственной волны — и второй не будет
никогда. Заход владельца 252 с втроём: `wavesCleared = 0`, то есть за весь
матч отработала ровно одна волна из десяти мобов на арену 94 025 м². После
активации Директора дефект неизлечим: он и свита живут в ядре постоянно,
`MobCount == 0` недостижим в принципе.

В задачу входит: независимая каденция волн на каждое кольцо; окно тишины,
которое **зарабатывается** зачисткой кольца; сложность, привязанная к **часам
захода**, а не к числу пришедших волн; полноразмерная волна на кольцо вместо
дележа одного бюджета весами; **сглаживание притока** (волна не садится в один
тик); потолок численности на кольцо, связанный правилом с физическим потолком
арены; приписка моба к кольцу, по которой считается «кольцо вычищено»;
молчание ядра на время Директора; таймеры в целых тиках; анонс волны в HUD; перепин трёх
эталонов.

**Вне задачи:** истощение секторов (ADR-001 §3.1 п. 2 — решение С6 Этапа 3 в
силе); радиус агрессии и патрулирование мобов (§3.11); спавн по площади
кольца (решение владельца К4, §3.11); обрезка «бумажных» потолков
(`MaxMobs`/`MaxProjectiles`/`MaxEventsPerFrame`/`MaxPickups`) — отдельной
задачей **после** замера (§11 п. 3); пространственная сетка расталкивания и
индекс `id → слот` в сборщике снапшота (§8 Р-А, §11 п. 4); анонс с указанием
кольца (потребовал бы второго подъёма `ProtocolVersion` за этап).

**Задача не является таском плана Этапа 3.** Дефект найден после написания
плана, трогает `Simulation` и двигает все три эталона — поэтому пайплайн
полный: brainstorm → спека → план → импл (AGENT.md §5). Порядок относительно
Ф9 решён владельцем: `app-ggvz` **вперёд** Ф9, иначе пачку амендментов ADR
пришлось бы вносить дважды.

## 2. Зафиксированные решения (brainstorm 2026-08-23)

| # | Тема | Выбор владельца |
|---|---|---|
| К1 | Что двигает волну | **Таймер, и он идёт всегда.** Зачистка кольца не отменяет паузу, а **перезапускает её с полного значения** — окно тишины зарабатывается (поправка агента, принята владельцем). Не вычистил — волна приходит по расписанию и ложится сверху |
| К2 | Пауза | **Своя на кольцо: внешнее 20 с, среднее 30 с, ядро 30 с.** Первое предложение 60/40/30 отклонено владельцем дословно: «60 сек на первом кольце — очень много, мобы с 3 выстрелов разваливаются» |
| К3 | Размер волны | **Полная волна в каждое кольцо** по существующей формуле; общий бюджет и его дележ весами удаляются |
| К4 | Где рождаются | **На окружностях колец, как сегодня.** Спавн по площади отклонён владельцем; довод принят: радиуса агрессии нет, мобы сходятся сами, а спавн по площади рождал бы мобов в поле зрения (`MinSpawnDistanceToPlayer` 8 м против `SightRadius` 45 м) |
| К5 | Старт | **Стартовая волна ×4:** `BaseCount` 4 → 16. Дословно: «надо не в 2 раза больше мобов на старте, а раза в 3-4, ИХ СЕЙЧАС ТАМ ВООБЩЕ НЕ ОЩУЩАЕТСЯ» |
| К6 | Потолок живых | **На кольцо: 150 / 110 / 10.** `MaxMobs 1350` остаётся физическим потолком массивов, связывается с потолками колец правилом валидации |
| К7 | «Кольцо вычищено» | **По кольцу приписки моба** (новое поле состояния), а не по тому, где он стоит сейчас |
| К8 | Ядро при Директоре | **Замолкает.** Переезд бюджета ядра в среднее кольцо (Р253) отменяется |
| К9 | Эталоны | **Перепин №4 разрешён** владельцем, отдельным коммитом |
| К10 | Анонс волны | **В скоупе, без указания кольца** — провод и `ProtocolVersion` не трогаем |

### 3.2. Симуляция: три волны вместо одной

Сегодня `SimulationWorld` держит **один** `WaveState` (`:143`,
инициализация `:293`), доступ через свойство `WaveRef` (`:1026`), и долг лежит
матрицей девяти полей `Pending{Зона}{Архетип}` (`SimStates.cs:338-340`,
введена Т11 Этапа 3 ради дележа одного бюджета по трём зонам).

**Становится: три экземпляра `WaveState`, по одному на кольцо, и матрица
девяти полей снова распадается на три поля внутри каждого** — зона переезжает
из имени поля в индекс экземпляра. Это не рост состояния, а его перекладка.

```csharp
public struct WaveState
{
    public WavePhase Phase;
    /// НЕ счётчик волн (Р334): шаг сложности той волны, которая идёт в этом
    /// кольце сейчас — присваивается из часов захода в StartWave.
    public int WaveIndex;
    /// Целые тики, не секунды (R-178/R-190, урок 348) — см. §3.3.
    public int PhaseTicks, AliveCount;
    public int PendingChaser, PendingGunner, PendingElite;
    public int PendingTotal => PendingChaser + PendingGunner + PendingElite;
}
```

- **`WaveIndex` ОСТАЁТСЯ, но перестаёт быть счётчиком** (Р334, поправка v4 к
  Р315): при старте волны кольцо **присваивает** туда шаг сложности из часов,
  а не инкрементит. Поле честное (это «волна какого шага идёт здесь сейчас»),
  из мира не выводится, и Р315 исполняется целиком — отставать от часов оно
  больше не может. Первая редакция убирала поле вовсе и вводила взамен
  `RenderSnapshot.WaveNumber`; ревью плана показало, что это ломает
  компиляцию четырёх сборок (`HudController`, `NetworkSimBackend.ReadWave`,
  `SnapshotAssembler`, `LongRunHarness`) ради нулевой выгоды.
- **`PhaseTimer` (float) → `PhaseTicks` (int)** (Р316, находка C-Important).
  В коде проекта записано правило: целые тики — «единственная единица, в
  которой детерминированное сравнение имеет право производиться»
  (`SimulationWorld.TicksFromSeconds`, `:20-40`, R-178/R-190, урок 348), и
  фаза Ф5 заплатила за него дважды измерением. v1 сохраняла
  `float PhaseTimer -= TickDt; if (<= 0f)` и о правиле молчала. Перепин №4
  всё равно санкционирован — перевод бесплатен именно сейчас, а позже стоил
  бы перепина №5.
- `PendingTotal` остаётся **вычисляемым свойством, а не полем** (R-52/Р206:
  автосвойство завело бы скрытое backing-поле, невидимое и `HashWave`, и
  рефлексивному свипу `WorldLifecycleTests`).
- `AliveCount` — живые мобы **этого кольца**; величина производная
  (считается сканом, §3.5), но поле историческое и хешируется с Т5.
  ⚠ v1 писала «его читают `DevOverlay` и провод» — **неверно** (находки
  A/B-Minor): `DevOverlay` волну не читает вовсе, единственный читатель —
  `SnapshotAssembler.cs:1715`. Утверждение унаследовано из устаревшего
  комментария `WaveSystem.cs:85-90`, который правится этой же задачей.
- Хранение: `WaveState[] _waves` длиной `Zones.Count`, аллоцируется один раз
  в конструкторе; доступ `internal ref WaveState WaveRef(Zone zone) => ref
  _waves[(int)zone];`
  ⚠ **Свойство становится методом, и это рвёт симметрию пары** (находка
  B-Minor): `WaveRef` (`:1026`) и `MatchRef` (`:1032`, док `:1029`) написаны как пара, и
  док `MatchRef` ссылается на `WaveRef` формулировкой «same ref-return
  pattern». Оба комментария перецеливаются в том же таске.
- **`Zones.Count` — один дом для числа колец** (`SimConfig.cs`, рядом с
  `enum Zone`). Форма — статический класс, а не `const` на структуре
  конфига: рефлексивный свип `SimConfigHashTests` (`:275`) ходит
  `GetFields()` с дефолтными биндингами и видит статику. Ближние прецеденты
  той же формы лежат в том же файле — `ItemCatalogLookup` (`:458`) и
  `LootTransferTimes` (`:596`) (находка B-Minor; v1 ссылалась на дальние
  `ExtractKinds`/`ProjectileIds`).
  Поглощаются **две** копии тройки: `WaveSystem.ZoneCount` (`:36`) и
  `LootDrops.ZoneCount` (`:79`) вместе с зеркальным доком
  `SimConfig.cs:522-523` (находка B-Minor).
- **`WorldSave.Wave` → `WorldSave.Waves`** (массив длиной `Zones.Count`).
  ⚠ Идиома копирования называется **пофайлово** (находка B-Important; v1
  писала «поэлементно» и указывала на неверный метод):
  `System.Array.Copy` — идиома `SimulationWorld` (`:2141`, `:2249`, `:2312`);
  цикл `for` — идиома `RenderSnapshot.CopyFrom` (`:409-449`). Массив в
  инициализаторе `SaveState` аллоцируется по образцу
  `Mobs = new MobState[_mobs.Length]` (`:2222`).
  ⚠ **v1 назвала неверный адрес** (находка A-Critical/B-Critical):
  `SimulationWorld.cs:2166` — это `target.Wave = _wave` внутри
  **`CaptureSnapshot`** (метод начинается `:2111`), а `SaveState` (`:2206`)
  пишет волну на **`:2238`**; `RestoreState` — `:2328`. По ссылке v1
  исполнитель починил бы не тот метод и оставил бы `WorldSave` алиасить живой
  массив — ровно тот дефект, против которого стоит предупреждение.
  **`CaptureSnapshot` при этом массива не получает вовсе** — он кладёт в
  снимок агрегат (§3.9), то есть алиасинга там нет по построению.
- Швы: `SetWaveForTest(Zone zone, in WaveState w)` — индексная перегрузка
  ложится в существующую форму `SetPlayerForTest(int, …)`/`SetMobForTest(int, …)`
  (`:2343-2371`).
- **Канонический порядок хеша** (`SimulationWorld.cs:2470`) — три шага
  `HashWave` подряд в порядке `Outer → Middle → Core`, на **том же месте**
  последовательности, где сегодня стоит один:

```
tick -> spreadRng -> waveRng -> lootRng -> nextEntityId -> playerCount
-> players[0..n) -> mobCount+mobs -> projectileCount+projectiles
-> pickupCount+pickups -> containerCount+containers+containerSlots
-> waves[Outer] -> waves[Middle] -> waves[Core] -> matchState
-> worldStats -> stats[0..n) -> inventories[0..n)
```

- **Горячая правка** (находка D-Minor): `SimulationWorld.ApplyConfig`
  оставляет состояние волн нетронутым и не сравнивает `WaveSimConfig` в
  `ArenaTopologyMatches`. Следствие называется прямо: правка
  `WavePauseByZone` в PlayMode оставляет до трёх уже заряженных таймеров
  дотикать старым значением, а понижение `MaxAliveByZone` ниже текущего
  населения замораживает спавн кольца до естественной убыли. Это **принятое**
  поведение (то же, что у прочих таймеров мира), и оно получает свой кейс в
  `HotTweakTests`, чтобы быть решением, а не дрейфом.

### 3.3. Симуляция: каденция, зачистка, окно тишины

**Правило одной фразой:** таймер кольца идёт **всегда**; когда он дошёл до
нуля — кольцо получает волну; если кольцо вычищено раньше срока — таймер
**перезапускается с полного значения**, и это и есть заработанное окно тишины.

⚠ **Сложность при этом от зачисток НЕ зависит** (Р315, находка C-Critical).
v1 брала размер волны и долю элиты от счётчика волн кольца — а счётчик растёт
только при старте волны, то есть каждая зачистка отодвигала бы кривую
сложности на целую паузу: **хорошо играющий встречал бы волны слабее, чем
пассивный.** ADR-001 §3.1 говорит обратное и дословно: «Сложность привязана к
часам, ценность — к месту», «каждая волна **везде** сильнее предыдущей».
Поэтому вводится **шаг сложности от часов захода**:

```
step = 1 + max(0, tick - TicksFromSeconds(FirstWaveDelay))
             / TicksFromSeconds(DifficultyStepSeconds)     // целочисленно
```

`DifficultyStepSeconds` = 20 с (`.asset`), то есть равен паузе внешнего
кольца — при нуле зачисток числа совпадают с v1 ровно, а при зачистках кривая
больше не проседает. Шаг **нигде не хранится** (Р206): это чистая функция
тика, вычисляемая там, где нужна.

Тик `WaveSystem.Update`:

1. **Существующий ранний выход не трогается:** нет ни одного живого носителя
   (`Targeting.NearestAlivePlayer`, `:50`) — не тикает ничего. Существующий
   свидетель этого правила уже есть и переиспользуется, а не пишется заново:
   `WaveScalingTests.NoAlivePlayers_WaveDirectorFreezes_PhaseAndTimerStandStill`
   (`:222`, находка D-Important).
2. **Один проход по мобам** считает живых по кольцам приписки (§3.5) в
   `Span<int> alive` длиной `Zones.Count` (`stackalloc`, без аллокаций).
3. Для каждого кольца в фиксированном порядке `Outer → Middle → Core`:
   - **Неактивное кольцо замораживается идемпотентно:** `Phase = Waiting`,
     `PhaseTicks = 0`, три счётчика долга обнуляются, `AliveCount` пишется
     как есть — и переход к следующему кольцу. Неактивно кольцо в двух
     случаях: беззонная арена (`Arena.ZoneRadius.Length < 2`) — активно
     **только** `Zone.Outer`; и `Zone.Core` при `w.Match.Phase != Farm`
     (§3.6). Обнуление каждый тик, а не по детекции перехода: не нужно
     хранить «а было ли активно вчера», и состояние не носит фантомного
     долга кольца, которое больше никогда не заспавнит.
     ⚠ Формулировка точная (находка D-Minor): заморозка происходит «каждый
     тик, **в котором кто-то жив**» — ранний выход п. 1 стоит выше, поэтому
     кольцо, замороженное в `Active` на тике всеобщей смерти, донесёт долг
     через мёртвый отрезок. Безвредно (заход кончается), но записано.
   - `PhaseTicks--`.
   - `PhaseTicks <= 0` → `StartWave(зона)`: долг **назначается** (не
     накапливается, Р305), `Emit(WaveStarted, …, step)`, `Phase = Active`,
     `PhaseTicks = TicksFromSeconds(cfg.WavePauseByZone[зона])`.
   - Если `Phase == Active` — спавн долга: архетип-минорный порядок
     `Chaser → Gunner → Elite` (R-50, сохранён), **не более
     `cfg.MaxSpawnsPerZonePerTick` спавнов за тик на кольцо** (§3.4), неудача долг
     не трогает (существующее правило «полностью заблокированное кольцо не
     вешает тик», `:316-323`). Каждый успешный спавн инкрементит
     `alive[зона]` — иначе потолок §3.4 переехали бы внутри одного тика.
   - **Зачистка:** `Phase == Active && PendingTotal == 0 && alive[зона] == 0`
     → `WorldStats.WavesCleared++`, `Emit(WaveCleared, …, step)`,
     `Phase = Waiting`, **`PhaseTicks = TicksFromSeconds(WavePauseByZone[зона])`**
     — полное окно, даже если до срока оставалось меньше.
   - `wave.AliveCount = alive[зона]` — после спавна, как сегодня (`:91`).
4. `WorldStats.WavesCleared` остаётся **одним счётчиком на мир**: зачистка
   любого кольца растит его на единицу. Экран итогов
   (`DeathOverlayController.cs:407`, «Волн отражено: N») читает его без правки
   и наконец перестаёт показывать ноль.
   ⚠ **Семантика счётчика при этом меняется**, и это решение, а не дрейф
   (находка C-Minor): при трёх независимых циклах он означает «зачисток
   колец», а не «волн». С учётом §8 Р-Б он будет считать почти исключительно
   зачистки среднего и раннего внешнего кольца. Подпись экрана остаётся
   прежней — «Волн отражено» читается верно и в новом смысле.

**Стартовое состояние:** все три кольца `Phase = Waiting`,
`PhaseTicks = TicksFromSeconds(FirstWaveDelay)` (2.5 с = 75 тиков), одно число
на все кольца — кольца разойдутся сами разными паузами.

**RNG.** Поток один (`w.WaveRng`), потребляется в фиксированном порядке
кольцо-мажор/архетип-минор — детерминизм сохраняется тем же способом, что и
сегодня; число draw'ов остаётся чистой функцией состояния.

### 3.4. Симуляция: размер волны, сглаживание притока, потолок численности

**Формула размера не трогается** (`WaveSystem.CountForTest`, `:102-109`):
`round((BaseCount + CountGrowth · индекс₀) · (1 + (игроков−1) · PerPlayerCountFrac))`,
срезанная `MaxMobsPerWave`. Меняется только её вход: вместо «номер волны этого
кольца минус один» подставляется `step − 1` из §3.3, и вызывается она по разу
на кольцо.

**Состав внутри кольца не трогается** (`EliteShareFor`, `:277-284` + существующая
формула `GunnerShare`) — но её индекс тоже становится `step`, по той же
причине (Р315).

**Долг назначается, а не копится** (Р305). Сегодня присваивание корректно
потому, что новая волна начиналась только на пустом долге; с таймерной
каденцией волна может прийти на непустой долг, и тогда остаток
**перезаписывается**: копящийся долг на кольце у потолка рос бы неограниченно
и разрядился бы весь разом при первом же разрежении.

⚠ **Приток сглаживается: `MaxSpawnsPerZonePerTick`** (Р317, находка C-Critical).
v1 позволяла всей волне сесть в **один** тик (33 мс), и это расходится со
всеми названными референсами жанра — они без исключения размазывают спавн
(Killing Floor — сквады по таймеру, L4D — `director_spawn_interval` под
лимитом популяции, Risk of Rain — одна покупка за интервал). Три следствия
разом: пик процессора в тике прихода волны; до 72 новых записей мобов в одном
кадре против байтового бюджета соединения (`SnapshotMaxBytes 1000`,
`MobRecordBytes 9` — не влезшее **дропается** и учитывается счётчиком
`DroppedEntities`, `SnapshotAssembler.cs:104`, `:384`; `:1678-1684` — это бюджет
СОБЫТИЙ, не записей мобов);
и «убил тридцать у потолка — тридцать вернулись в том же тике» из
неперезаписанного долга, то есть ровно та бомба, от которой отказывался Р305.
Число — `WaveSimConfig.MaxSpawnsPerZonePerTick` = **2** на кольцо: волна в 72 моба
доезжает за 36 тиков (1.2 с), то есть **под собственный анонс** (§3.10).
Детерминизм не страдает: порядок кольцо-мажор/архетип-минор и число draw'ов
остаются функцией состояния. ⚠ Внести это сейчас обязательно: сглаживание
двигает хеш, а после перепина №4 санкций больше нет (§4).

**Потолок численности — на кольцо** (`WaveSimConfig.MaxAliveByZone[3]`).
Гвард стоит **перед** поиском места, ровно там же и по той же причине, что и
существующий резерв Директора (`:312-318`), и **не трогает**
`WorldStats.MobSpawnsSkipped` — этот счётчик означает «мир упёрся в свой
ФИЗИЧЕСКИЙ потолок» (контракт `SpawnMob` с Т5 Этапа 2), а потолок кольца —
политика директора волн. Долг остаётся, ретраится следующим тиком.

**Существующий резерв Директора не трогается:**
`MobCount >= Arena.MaxMobs − Flow.DirectorReserveSlots`.

⚠ **Инвариант, названный прямо** (находка D-Important): **кольцо, чей потолок
ниже размера волны, не бывает вычищено никогда** — его долг не может
обнулиться, `Phase` остаётся `Active`, окно тишины для него не существует, и
`WavesCleared` от него не растёт. Для ядра это штатно и намеренно: потолок 10
против волны в 38 элит — гарнизон, а не зачищаемая зона. Требуется тест
«кольцо с потолком ниже размера волны **не вешает тик** и корректно ретраит
долг» (§4).

**Числа (`.asset`, решения К2/К5/К6 + Р315/Р317):**

| Число | Было | Стало | Обоснование |
|---|---|---|---|
| `BaseCount` | 4 | **16** | К5. При троих первая волна кольца — `round(16·2.4) = 38` мобов, то есть **86 живых на арене** через 2.5 с после старта (ядро срежется своим потолком) против сегодняшних десяти на всю арену |
| `WavePauseByZone` | `WavePause 4` (одно на арену) | **`[20, 30, 30]`** | К2 |
| `MaxAliveByZone` | нет | **`[150, 110, 10]`** | К6 |
| `MaxSpawnsPerZonePerTick` | нет (весь долг в один тик) | **2** | Р317. ⚠ Имя сведено с планом в v5: счётчик обнуляется НА КОЛЬЦО, и имя обязано это говорить (было `MaxSpawnsPerTick`) |
| `DifficultyStepSeconds` | нет (счётчик волн) | **20** | Р315; равен паузе внешнего кольца, поэтому кривая совпадает с v1 при нуле зачисток |
| `EliteShareOuterGrowth` | 0.02 | **0.007** | §11 п. 1 — пересчёт под новую паузу |
| `ZoneWeights` | `[0.45, 0.45, 0.10]` | **удаляется** | К3 |
| `CountGrowth`, `MaxMobsPerWave`, `PerPlayerCountFrac`, `GunnerShare*`, `EliteShareMiddle`, `EliteShareOuterCap`, `SpawnRingInset`, `MinSpawnDistanceToPlayer`, `MaxSpawnAttempts`, `FallbackSlots`, `FirstWaveDelay` | — | **не трогаются** | правило 3 |

**Что эти числа означают в бою** (арифметика, а не ощущение):

- Рост волны при троих по шагам сложности: 38 → 43 → 48 → 53 → 58 → 62 → 67 →
  **72** (потолок одной волны) на восьмом шаге, то есть через
  `2.5 + 7·20 = 142.5 с` ≈ 2.4 минуты.
- Потолок внешнего кольца достигается, если его не чистить, **к концу первой
  минуты**: волны приходят на 2.5-й, 22.5-й, 42.5-й и 62.5-й секунде,
  накопленным итогом 38 → 81 → 129 → упор в 150. Потолок означает «насколько
  плохо станет, если забить на кольцо», а не «сколько их бывает».
- Экономика боезапаса плотность выдерживает с запасом: чейзер — 30 HP, это
  3 попадания при `Damage 12`, а роняет одну ячейку = 10 выстрелов. Элита —
  120 HP (10 выстрелов) при 4 ячейках. Ограничитель плотности — выживание
  носителя и процессор, не патроны.
- Ядро при потолке 10 — это 10 элит, то есть 100 выстрелов на зачистку **до**
  самого Директора (2500 HP). ⚠ Побочное следствие, названное прямо (находка
  D-Minor): `MatchFlowSystem.LiveRetinueCount` считает элит, **стоящих** в
  ядре, поэтому на момент активации там штатно уже 10 волновых элит и
  `TopUpRetinue` оказывается no-op — «свита» фактически становится остатком
  последней волны ядра. Это согласуется с Р215 (свита — позиционное понятие),
  но это поведенческое изменение, и оно получает тест.
- Сумма потолков `150 + 110 + 10 = 270` против фактических **десяти** живых
  сегодня.
- **Потолок одной волны 72 работает как вторая награда за зачистку** (Р331):
  кольцо, вычищенное досрочно, возвращается к своему потолку не мгновенно, а
  примерно за две волны — то есть скилл покупает не только тишину, но и
  ослабленную арену на следующие полминуты.
- ⚠ Потолок кольца имеет физическую границу сверху, которую валидация не
  проверяет (находка D-Minor): спавн идёт по окружности, и потолок выше того,
  что окружность способна упаковать, превратился бы в вечный неразряжаемый
  долг — тот же класс дефекта, что урок 421. Сегодня запас большой (1 074 м
  внешней окружности против 150 тел радиусом 0.5–0.8 м), поэтому правило не
  вводится, но граница названа.

**Пересчёт элитной кривой периферии** (Р311, вопрос §11 п. 1). ADR-001 §3.1
обещает: «на 12-й минуте на периферии дерёшься с мобами среднего уровня».
Доля элиты внешнего кольца растёт `EliteShareOuterGrowth · (step − 1)` до
`EliteShareOuterCap 0.25`, то есть упирается в потолок на шаге
`1 + 0.25/growth`. При старом `0.02` это шаг **13.5 → 14** (при паузе 4 с это
было недостижимо вовсе, волн не было; при шаге 20 с — **4.5 минуты** вместо
канонных двенадцати). `0.007` кладёт потолок на шаг **37**
(`0.007·36 = 0.252 ≥ 0.25`), то есть на `2.5 + 36·20 = 722.5 с` = **12.0
минут** — канон исполняется буквально. ⚠ Число одно и то же во всех разделах
спеки: **шаг 37, 722.5 с, 12.0 минут** (v1 расходилась сама с собой: «волна
37» в одном месте, «волна 36» и «12.2 минуты» в других — находки A/D).
Благодаря Р315 расчёт теперь **точен по построению**: зачистки его больше не
сдвигают.

### 3.5. Симуляция: кольцо приписки моба

«Кольцо вычищено» нельзя считать по тому, где моб стоит: радиуса агрессии
нет, каждый моб идёт к ближайшему живому носителю (`MobAiSystem.cs:52`), и
через полминуты вся волна среднего кольца окажется во внешнем. Считать по
месту — значит подарить бесплатную зачистку центра тому, кто выманил всех
наружу.

**`MobState` получает поле `Zone SpawnZone`** — кольцо, **в которое моб был
поставлен спавнером**. Не «рождён волной», а именно приписка: Директор и
свита приписаны к ядру, потому что поставлены в ядро.

- **Ставится параметром, а не геометрией.** `SpawnMob(MobType type, float2
  pos, Zone zone)` (`SimulationWorld.cs:1924`); вызовы:
  `WaveSystem.SpawnPendingOfType` — своё кольцо; `MatchFlowSystem.cs:123`
  (Директор) и `:214` (свита) — `Zone.Core`.
  Альтернатива «вывести из позиции через `Geometry.ZoneOf` внутри
  `SpawnMob`» отклонена: она падает на беззонной арене (`ZoneOf` читает
  `ZoneRadius[0]/[1]` без гварда, `Geometry.cs:297-303`, урок 315), и она
  пересчитывает из геометрии то, что спавнер знает намеренно.
- ⚠ **Цена смены сигнатуры названа числом** (находки A/B/D-Important):
  `SpawnMobForTest` — **122 вызова в 18 тестовых файлах** (127 вхождений
  идентификатора, пять из них — упоминания в доках; пересчитано в ре-ревью).
  Решение:
  **у производственного `SpawnMob` третий параметр обязателен и умолчания не
  имеет**, а тест-шов `SpawnMobForTest(MobType, float2, Zone zone =
  Zone.Outer)` получает **хвостовой параметр с умолчанием** — ровно та
  конвенция, которую план Этапа 3 записал в Global Constraints («новые
  параметры существующих хелперов — только хвостовыми с умолчанием»). Так 127
  вызовов не двигаются, а продакшен остаётся явным. Риск умолчания (док

### 3.6. Симуляция: ядро и Директор

**Ядро замолкает с активации Директора и не возвращается** (К8). Гвард —
существующий `w.Match.Phase != MatchPhase.Farm` (тот же, что у Р185 и
`app-d2ki`): защёлка односторонняя, поэтому одна проверка говорит и «ядро
принадлежит Директору с момента пробуждения», и «волны туда не вернутся
после его смерти» — окно дележа над телом обязано пройти без свежих элит.

**Переезд бюджета ядра в среднее кольцо (Р253, `WaveSystem.cs:146-150`)
удаляется** (Р312), и это не упрощение ради упрощения. Р253 переносил долю
ядра в среднее, чтобы волна «не худела» при дележе одного бюджета. С
независимыми волнами делить нечего: у среднего кольца **своя полная волна**,
и переезд означал бы её **удвоение** ровно в тот момент, когда трое дерутся с
боссом, — прямо против того соображения, ради которого Р253 и заводился.

Резерв слотов Директора (`DirectorReserveSlots 3`) не трогается.

### 3.9. Провод и снимок: блок волны остаётся МИРОВЫМ

⚠ **v1 предлагала сделать блок персональным (нести волну кольца
наблюдателя). Решение отменяется** (Р318) по трём независимым причинам, две
из которых — факты кода:

1. **Обоснование v1 было ложным.** Она писала «сборщик читает не мир, а
   снимок». Сборщик держит `SimulationWorld _world`
   (`SnapshotAssembler.cs:268`, `:604`) и уже берёт из него позицию
   наблюдателя: `_viewpointPos = _world.PlayerAt(viewpointIndex).Pos`
   (`:883`). То есть аргумент, на котором стояла вся конструкция, неверен
   (находка C-Important).
2. **Локальная половина была неисполнима.** v1 поручала заполнение
   наблюдаемой волны бэкендам, а `LocalSimBackend` наблюдаемого места **не
   знает**: `ObservedIndex` живёт в `SimulationRunner` (`:647`, резолвится
   `:1379-1459`), и `NetworkSimBackend` пишет об этой границе прямым текстом
   (`:101-107`) (находки A/B-Critical).
3. **И главное — персональный номер волны вреден.** `Geometry.ZoneOf` — жёсткий
   порог без гистерезиса (`:297-303`). Носитель, идущий вдоль `r = 130`,
   получал бы поочерёдно номер среднего и внешнего кольца, а при движении
   внутрь число **падало** бы. Немонотонный счётчик волн без подписи кольца
   читается как дефект; стандарт жанра — счётчик глобальный и монотонный
   (находка C-Important).

**Как вместо этого:**

- **Номер волны — мировой и монотонный:** агрегат берёт **максимум**
  `WaveIndex` по трём кольцам. Шаги сложности только растут, поэтому число
  монотонно по построению.
  ⚠ **Остальные поля агрегата определяются ТОЧНО** (Р338, находка ре-ревью
  В4 — «минимум среди активных» имело два прочтения, и одно из них ломается):
  `Phase = Active`, если хоть одно кольцо в `Active`; `PhaseTicks` = минимум
  среди **НЕЗАМОРОЖЕННЫХ** колец (замороженное кольцо несёт `PhaseTicks = 0`
  по §3.3, и «минимум по всем» давал бы вечный ноль на беззонной арене и при
  живом Директоре), а если незамороженных колец нет — **0**; `AliveCount` и
  три `Pending` — суммы по всем кольцам. Каждое из четырёх правил получает
  ассерт (§4). ⚠ **Нового поля в снимке не появляется** (Р334):
  `RenderSnapshot.Wave.WaveIndex` уже есть, уже едет по проводу и уже читается
  HUD'ом — правки клиентского декодера, сборщика, HUD и харнесса не нужны
  вовсе.
- **`RenderSnapshot.Wave` остаётся ОДНИМ `WaveState`** и несёт **агрегат
  мира**, вычисляемый в `CaptureSnapshot`: `Phase = Active`, если активна
  хоть одна волна; `PhaseTicks` = минимум оставшегося среди активных колец
  («сколько тиков до ближайшей волны»); `AliveCount` = сумма; три `Pending` —
  суммы. Это производная величина в нехешируемом снимке, у неё один смысл и
  один дом. Массива в снимке **не появляется** — значит не появляется и
  проблемы рефлексивного сторожа `ArrayCountField` (находка C-Important) и
  риска алиасинга в `CaptureSnapshot`.
- **Провод не меняется ни на байт:** блок волны — те же 4 байта
  (`SnapshotBlocks.cs:112`), `phase` = фаза агрегата, `waveIndex` u16 =
  `WaveIndex` агрегата (максимум по кольцам), `aliveCount` u8 = сумма живых.
  `ProtocolVersion` остаётся 3, и **сборщик не меняется ни строкой** (Р334).
- ⚠ **Байт живых насыщается и об этом надо сказать честно** (находки
  C/D-Minor): 270 > 255, писатель уже режет через
  `math.min(..., byte.MaxValue)` (`SnapshotAssembler.cs:1715`), а **читателя у
  этого числа сегодня нет вообще** — клиент кладёт его в
  `slot.Wave.AliveCount` (`NetworkSimBackend.cs:2183`) и никто не читает.
  Поэтому: поле остаётся насыщающимся, его док это говорит, и заводится
  side-quest «расширить или снять мёртвый байт при следующем подъёме
  протокола». Правило валидации «потолок ≤ 255», которое предлагала v1,
  **снимается** — оно защищало несуществующего читателя и мешало бы владельцу
  поднять потолок кольца выше 255 на плейтесте.
- `Editor/LongRunHarness.cs:82` (`snapshot.Wave.WaveIndex`) **не трогается** —
  теперь он логирует шаг сложности, что и требовалось.
- Хелпер `Geometry.ZoneOfOrOuter`, который вводила v1, **не нужен** и не
  заводится: единственным его потребителем был отменённый персональный блок.
  ⚠ Существующее дублирование гварда беззонной арены при этом остаётся и
  **не трогается** (находка B-Important): у четырёх мест разная семантика
  (`MatchFlowSystem.cs:94`/`:197` — `return`, `MobAiSystem.cs:379` —
  `NoLeash`, `GreyboxBuilder.cs:267` — `HasZones`), общий хелпер их не
  поглощает, и это записано, чтобы следующий автор не пытался.

### 3.10. Presentation: номер волны и вспышка анонса (К10)

Канон ADR-001 §3.1 описывает ритм как «анонс хозяина → волна → окно тишины».
Сегодня события `WaveStarted`/`WaveCleared` **никто не показывает**: они
доезжают до клиента (`ClientEventDecoder.cs:354-364`), и на этом всё.

⚠ **v1 предлагала импульс по событию `WaveStarted`. Отменяется** (Р322,
находка C-Important): эти события идут каналом `DeliveryChannel.All`
(`EventRelevance.cs:72-83`) — то есть игрок на периферии получал бы анонс
волны ядра, а при трёх кольцах это ~7 строк в минуту при показе 2.5 с, и
строка горела бы почти постоянно, перестав быть событием. Коалесценция лечит
наложение, а не нерелевантность. Плюс `NetConfig.SnapshotEventBudget = 16`
(находка D-Important): совпавший тик трёх колец даёт до 216 `MobSpawned` того
же ранга, и анонс выживал бы только за счёт неявного порядка эмита.

**Как вместо этого — от состояния, а не от события:**

- Строка `_waveText` (`HudController.cs:202`) продолжает показывать
  «ВОЛНА N», где `N = curr.Wave.WaveIndex` — **мировой, монотонный, растущий
  строго по часам захода**. Дребезга на границе колец нет по построению.
- **Анонс — вспышка этой же строки в момент, когда N вырос**: одна вспышка
  на шаг сложности, то есть раз в 20 с, независимо от числа колец. Никакой
  очереди, никакой нерелевантности, ноль байт провода, ноль изменений в
  маршрутизации событий.
- **Правило вспышки живёт в чистом статическом шве и получает EditMode-тест**
  (находка D-Important; v1 отговаривалась «MonoBehaviour в EditMode не
  поднимается»). Прецедент прямо в проекте: `Tests/EditMode/HudPhaseLineTests.cs`
  тестирует `HudController.PhaseWord`/`Clock` как чистые функции.
- Секунды вспышки — `GameFeelConfig.WaveAnnounceSeconds` (дефолт 1.5 с), а не
  код-константа: CRITICAL RULE 6 требует балансовых чисел в SO, и владелец
  крутит их на плейтесте. ⚠ Идиома импульсов в `HudController` описана в v1
  неверно (находки A/B-Minor): из `GameFeelConfig` секунды берёт только
  `_staminaDeniedTimer` (`:329`), а `_pickupMaskTimer` — код-константу
  `PickupMaskSeconds = 1f` (`:115`), и декрементятся они в разных местах
  (`LateUpdate` `:245` против `UpdateStaminaBar` `:349-353`). Новый таймер
  декрементится в `LateUpdate` — это записывается, чтобы не появился третий
  паттерн.
- Гашение на `WorldRestarted` — в существующий список (`:364-384`).
  ⚠ Сегодня `_waveText` в этом списке нет (он переписывается каждый кадр);
  вспышка обязана войти, иначе первый кадр нового захода унаследует свечение.
- Маркер-ключ синка `GameFeelConfig` переезжает с `ContainerVisualScale`
  (`GameFeelConfig.cs:546`, `StageOneSceneBootstrap.cs:788`) на новое
  последнее поле — те же три вещи, что в §3.8.
- Текст подписи — цитата экранной надписи, русская строка в коде разрешена
  (прецеденты «Наблюдать», «Время на объекте», «Буст»).
- **Звук анонса** (находка C-Minor: канон называет это «анонс **хозяина**»,
  и в жанре это голос/стингер) — **вне скоупа**, заводится side-quest'ом:
  аудио-ассета под него нет, а выдумывать его на server-сессии — фича ради
  фичи. Строка со вспышкой закрывает К10 полностью.

### 3.11. Что осознанно НЕ делаем

- **Радиус агрессии и патрулирование.** Каждый моб идёт к ближайшему живому
  носителю с любого края арены, и это остаётся так (решение владельца К4
  опирается на этот факт). Отсюда следствие, которое надо смотреть на вехе:
  установившееся состояние — «поезд» из живых мобов за спиной носителя, а
  остальная арена пуста при **любой** геометрии спавна. Отдельная задача не
  заводится до плейтеста — сначала числа (правило 3), и веха В4 получает под
  это **отдельный критерий** (§5, находка C-Important).
- **Спавн по площади кольца** (К4). Условие пересмотра названо заранее: если
  на В4 при населении у потолка владелец снова пробежит кольцо и никого не
  встретит — лечим **числом** (пауза, потолок), и только если числа не
  помогли, возвращаемся к геометрии.
- **Истощение секторов** (ADR-001 §3.1 п. 2) — решение С6 Этапа 3 в силе.
- **Любая работа по производительности** (§8 Р-А) — только после замера,
  отдельными задачами: сетка расталкивания, индекс `id → слот` в сборщике и
  **снятие копии `MobSimConfig` в горячих циклах** (Р335 отменяет Р327). При 270
  агентах честный перебор пар в жанре нормален, а своя сетка была бы
  правильным решением, а не самописью (CR 1 закрывает `Simulation` от
  `Unity.Collections`/Physics2D).
- **Обрезка бумажных потолков** (`MaxMobs 1350` и спутники) — после замера,
  отдельной задачей (§11 п. 3).
- **Звук анонса** — §3.10, side-quest.
- **Второй подъём `ProtocolVersion`** — §3.9.

  По числам самой спеки размер волны упирается в `MaxMobsPerWave` 72 на шаге 8
  (2.4 мин), доля ганнеров насыщается на шаге 17 (5.4 мин), доля элиты
  внешнего кольца — на шаге 37 (12.0 мин). После двенадцатой минуты волны
  **перестают меняться вовсе**, а матч длится 15–20 минут; среднее кольцо
  застывает уже на шестой. Канон ADR-001 §3.1 «каждая волна везде сильнее
  предыдущей» исполняется, таким образом, первые двенадцать минут внешним
  кольцом и первые шесть — средним; дальше давление создаёт не волна, а
  накопленное население против потолков колец, то есть **отказ чистить**.
  Числа не трогаются (правило 3 и решение владельца Р331), но факт входит в
  §8 риском и в §9 амендментом — умолчать его значило бы оставить в ADR
  утверждение, которое новая механика делает наполовину ложным (правило 19).
  ⚠ Решение о рычаге (растущий `MaxMobsPerWave` или растущий потолок кольца) —
  **вопрос владельцу после вехи В4**, с числами плейтеста в руках.

## 8. Риски

- **Р-А. Процессор при 270 живых — не измерялся никогда.** ⚠ v1 назвала две
  системы из шести и занизила арифметику (находки C/D-Important). Полный
  список масштабирующегося от `MobCount`:
  - **расталкивание** — честный перебор пар без сетки
    (`SeparationSystem.cs:38-60`): ~36 тыс. пар/тик, и на каждой паре
    **копия `MobSimConfig` по значению** (~128 Б) — порядка 4.6 МБ/тик,
    139 МБ/с. ⚠ **В этой задаче НЕ лечится** (Р335 отменил Р327): работа
    уходит под гейт Р333, отдельной задачей после замера;
  - **`SnapshotAssembler.MobSlotOf`** (`:998`) — линейный скан по
    `_capture.MobCount` **на каждый видимый id** (`:1493`), то есть
    O(MobCount²) на соединение: ~219 тыс. сравнений при 270 мобах и троих
    клиентах против ~300 сегодня. Вероятно дороже расталкивания;
  - **`VisibilitySystem`** (`:73-84`) — проход по всем мобам с проверкой
    линии обзора на каждого наблюдателя;
  - **`ProjectileSystem`** (`:96-105`) — вложенный цикл «снаряды × мобы»;
  - **`MobAiSystem`** — `NearestAlivePlayer` и обход препятствий на каждого;
  - **фильтр спавна** — до `MaxSpawnAttempts + FallbackSlots` = **40**
    (не 16, как считала v1) оценок на единицу долга, каждая O(живых); после
    Р317 это `2 × 40 × 270 ≈ 21.6 тыс.` на кольцо в тик вместо 778 тыс.
  Митигация: **в этой задаче — только Р317** (сглаживание притока); замер
  **до** выдачи сборки;
  докладывается **измеренный** потолок, а не тихо срезанный; сетка и индекс
  `id → слот` — отдельными задачами после замера.
- **Р-Б. Заработанное окно может оказаться механикой первой минуты.**
  Внешнее кольцо садится на потолок к 62.5 с (§3.4), после чего зачистка
  требует снять 150 тел быстрее, чем приходит следующая волна. Тогда К1
  работает ~минуту из пятнадцати, а счётчик «отражено» снова будет низким —
  уже по честной причине. Критерий В4 п. 7 заведён именно под это; рычаг —
  потолок и пауза. ⚠ **Смягчается Р331:** вычищенное кольцо возвращается не
  сразу к потолку, а волнами по 72, то есть после зачистки есть ещё примерно
  две волны относительно спокойной арены — окно шире, чем одна пауза.
- **Р-К. Кривая сложности конечна: после 12-й минуты волны не меняются.**
  Размер упирается в `MaxMobsPerWave` 72 на 2.4-й минуте, доля ганнеров
  насыщается на 5.4-й, доля элиты периферии — на 12.0-й; матч 15–20 минут.
  Среднее кольцо застывает на шестой минуте (25 элит / 47 ганнеров / 0
  чейзеров и так до конца), ядро неизменно с первой секунды (100 % элиты).
  Последняя треть матча идёт на ровной кривой, и рост напряжения там даёт
  только накопление населения до потолков 150/110. Митигация на эту задачу —
  никакой (числа владелец закрыл, Р331); **критерий В4 п. 1 «ощущается ли
  плотность» проверяется ОТДЕЛЬНО в первой минуте и в середине захода** именно
  под это, а рычаг выбирается после плейтеста (Р340).
- **Р-В. Давление на подбираемое, а не на контейнеры.** ⚠ v1 оценивала
  трупы-контейнеры и завысила их в 5–10 раз (находка D-Minor):
  `ContainerKind.MobCorpse` рождается только при успешном броске
  `DropChance` (чейзер/ганнер 0.1). Настоящее давление — **`SpawnPickup`
  вызывается на КАЖДУЮ смерть** (`SimulationWorld.cs:1512`) при
  `PickupTtlSeconds 120` и `MaxPickups 1200`: темп подбираемого следует темпу
  убийств один-к-одному. Митигация — счётчики `PickupSpawnsSkipped`/
  `ContainerSpawnsSkipped` в замере (§7 п. 4); рычаги — TTL и капы.
- **Р-Г. «Поезд».** Радиуса агрессии нет, поэтому установившееся состояние —
  колонна за спиной носителя и пустая арена вокруг; игроку может быть
  выгодно НЕ чистить, а набрать поезд и оторваться (7.5 против 4–5.2).
  Критерий В4 п. 8; решение владельца по агре — после плейтеста.
- **Р-Д. Первая волна рождается в 12 метрах от стартового кольца.** Заход
  начинается сразу — это и цель К5, и риск «слишком резко». Рычаги —
  `FirstWaveDelay`, `MinSpawnDistanceToPlayer`.
- **Р-Е. Пересчитанная кривая элиты — расчёт, а не измерение.** Вкус
  владельца на В4.
- **Р-Ж. Несовместимость сборок.** `simConfigHash` меняется: клиенты
  `builds-f8` к новому серверу не подключатся.
- **Р-З. Перепин №4 ослабляет регрессионный сигнал.** Митигация — отдельный
  коммит, полный зелёный прогон до и после, письменное обоснование каждой из
  шести причин сдвига.
- **Р-И. Время прогона EditMode.** См. §4; защита — числа фикстур (Р325),
  контроль — замер времени в гейте.

## 9. Амендменты ADR (в пачку Ф9)

Вносятся **одной пачкой на финализации Этапа 3** вместе с уже накопленными
(`DirectorVisualScale`, `EliteVisualScale`, правило `app-d2ki`, новая
раскладка арены). Правка «по месту» запрещена (урок 250).

- **ADR-001, уточнение §3.1.** Ритм волн — не один цикл на арену, а
  **независимый цикл на каждое кольцо**. Окно тишины **зарабатывается**
  зачисткой кольца и длится `WavePauseByZone` (20/30/30 с) вместо
  «60–90 сек». Формулировка «каждая волна везде сильнее предыдущей»
  **сохраняется буквально** и исполняется единым шагом сложности от часов
  захода (Р315), а не счётчиком волн.
- **ADR-002, уточнение §8 Этап 3.** Зонный спавн-бюджет одной волны
  (`ZoneWeights`) заменяется независимыми волнами по кольцам с потолком
  численности на кольцо и ограничением притока на тик; общий `MaxMobs`
  объявляется физическим потолком массивов, связанным с потолками колец
  правилом валидации.
- **ADR-003, дополнение словаря §9** (находки A/D): вносятся строки
  «волна» (`Wave`), «кольцо» (`Zone`) и «партия» (user-facing термин анонса,
  цитата ADR-001 §3.1) — сегодня спека и HUD пользуются ими как терминами
  мира, а словарь их не содержит.
- **ADR-001, второе уточнение §3.1 — честная граница канона** (Р340).
  «Каждая волна везде сильнее предыдущей» исполняется **ростом единого шага
  сложности от часов захода**, но упирается в потолок одной волны
  (`MaxMobsPerWave`) на 2.4-й минуте и в потолки долей — на 5.4-й (ганнеры) и
  12.0-й (элита периферии). После двенадцатой минуты волна постоянна, и
  давление создаёт накопленное население против потолка кольца, то есть цена
  отказа чистить. Формулировка ADR остаётся, но получает эту границу явным
  текстом — иначе канон утверждает то, чего механика не делает.
- **Запись об отмене Р253** (переезд бюджета ядра) с обоснованием §3.6.

## 10. Декомпозиция bd

Задача `app-ggvz` (claimed) — родитель; сабтаски заводятся на фазе плана.

⚠ **v5: ЕДИНСТВЕННЫЙ ИСТОЧНИК ДЕКОМПОЗИЦИИ — ПЛАН, раздел «Декомпозиция bd»**
(восемь тасков в четырёх фазах). Семичастная разбивка, стоявшая здесь в v1–v4,
**отменена**: она резала работу по темам, а план перекроил её по
компилируемости (Р339), и сверка «спека против плана» по старому списку не
сходилась ни по одному таску. Ниже — только инвариант, который декомпозиция
обязана соблюсти, каким бы ни было число тасков:

1. **Приписка моба к кольцу — раньше всего, что её читает** (потолки, зачистка).
2. **Числа и правила валидации конфига — раньше каденции**, которая их читает.
3. **Форма состояния (три `WaveState`, тики, агрегат) — одним таском со ВСЕМИ
   своими читателями**, включая тестовую сборку (Р339).
4. **Гвард потолка и сглаживание — одним таском с тестами, которые их
   проверяют** (Р339: тест не едет в таск раньше своего механизма).
5. **Удаление весов и паузы — только когда исчез последний потребитель**,
   включая литералы фикстур `TestConfigs`.
6. **Числа в `.asset` и мёртвые ссылки — после того, как код перестал их
   читать**; C#-дефолты двигаются вместе с ассетом (Р337).
7. **Экран — после того, как агрегат даёт ему монотонное число.**
8. **Перепин №4 — последним и ОТДЕЛЬНЫМ коммитом** (R-23), вместе с правкой
   обоснования перепина №2; после него — гейт, замер, отчёт → **В4**.

Side-quest'ы — `bd create … && bd dep add <new> app-ggvz --type discovered-from`.

## 11. Вопросы владельцу — ЗАКРЫТЫ решением 2026-08-23

Владелец: «по рекомендованным тобой решениям, только ударь их о правила ещё
раз... и помни — ИГРАТЬ ДОЛЖНО БЫТЬ ВЕСЕЛО и интересно». Все четыре приняты в
рекомендованном виде; проверка правилами и вкусом добавила три следствия
(Р331–Р333, §6b), а не изменила ни одного выбора.

1. ✅ **`EliteShareOuterGrowth` 0.02 → 0.007.** Число калибровалось под
   механизм, которого не существовало, поэтому пересчёт — доведение починки
   до конца (правило 1), одна цифра в SO без нового механизма (правила 2/4),
   обоснование прямое — ADR-001 §3.1 (правило 3). По вкусу: при 0.02 дуга
   напряжения сгорает к 4.5-й минуте и десять минут идут ровно; при 0.007
   давление растёт весь заход. Монотонности первых минут не будет — растёт
   число мобов, а разнообразие доступно движением внутрь (среднее кольцо
   элитно с первой минуты, что и есть притяжение канона).
2. ✅ **`MaxMobsPerWave` 72 остаётся** — см. Р331.
3. ✅ **Обрезка бумажных потолков — после замера, отдельной задачей** — см.
   Р332.
4. ✅ **Две задачи производительности — после замера**, с решающим правилом
   Р333.
