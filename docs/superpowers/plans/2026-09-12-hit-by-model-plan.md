> **For agentic workers:** REQUIRED SUB-SKILL: `superpowers:subagent-driven-development`.
> Модели: implementer per task = **opus** — T1 (три примитива геометрии, 11 фикстур, 10 мутаций),

**Goal:** попадание, удар и реакция тела считаются по фигуре, которую игрок видит. Объём
попадания перестаёт быть соосным кругом и становится капсулой на паре костей, кости приходят
из запечённой таблицы поз, поза живёт в детерминированном состоянии и отматывается вместе с
позицией; удар моба проверяет фигуру и сектор перед собой; крен из знакового скаляра становится
вектором, отчего исчезает скачок картинки, который владелец назвал «читается как лаг или баг»;
попадание, дэш, слайд, столкновение и удар моба начинают давать **клип реакции** и угловой
импульс по одной физической формуле, без зонных правил (Н61).

**Architecture:** ядро остаётся чистым C# без `UnityEngine` (CR 1). Геометрия — **три новых
примитива** в существующем `Geometry` (`SegmentCapsule` как единственный солвер,
`PointCapsule` как его ветка, `ClosestPointOnSegment3` как единственный дом трёхмерного
клампа), разбор победителя — новый `HitVolumes` рядом с `HitZones`. Поза — **данные**:
`PoseTable` в `SimConfig`, ключ `PoseKey` (14 Б) собирается из плоских полей состояния
единственным упаковщиком и едет в истории отмотки. Клипы запекает редакторский пекарь на том
же сэмплировании, которым уже пользуется `SkeletonAudit`; целостность держат `ScriptedImporter`,
контрольная сумма из загруженных байтов и гейт «перепеки и сравни». Реакция — **обычный клип**:
он ложится в ту же таблицу, ключуется тем же `PoseKey`, отматывается тем же механизмом, и
объёмы следуют за ним сами. Провод растёт ровно на длину `PartId` у существующего вида события
и домен байта зоны, `ProtocolVersion` 5 → 6.

/// кандидаты. ⚠ Образец SegmentStadium раскладывается на ЧЕТЫРЕ ветки,

/// SegmentStadium и SegmentArc считают t == 1 промахом, а SegmentCircle —

/// вторая t ∈ [0,1), и на границе они расходятся НАМЕРЕННО.

public static float3 ClosestPointOnSegment3(float3 p, float3 a, float3 b, out float s)
{
    float3 d = b - a;
    float len2 = math.dot(d, d);
    if (len2 < 1e-12f) { s = 0f; return a; }   // вырожденный отрезок = точка
    s = math.clamp(math.dot(p - a, d) / len2, 0f, 1f);
    return a + d * s;
}

```csharp
public static bool SegmentCapsule(float3 p0, float3 p1, float padR,
    float3 a, float3 b, float capsuleR, out float t)
{
    t = 0f;
    float r = padR + capsuleR;
    // NaN на входе => false, без исключения. ⚠ Проверка стоит ПЕРВОЙ: ниже
    // идут сравнения, на которых NaN ведёт себя как «всё ложно», и ветка
    // «уже внутри» могла бы вернуть true на мусоре.
    if (!math.all(math.isfinite(p0)) || !math.all(math.isfinite(p1))
        || !math.all(math.isfinite(a)) || !math.all(math.isfinite(b))
        || !math.isfinite(r)) return false;

    float3 step = p1 - p0;
    // Ветка «нулевой шаг»: снаряд стоит. Это и есть PointCapsule, и она
    // ЗДЕСЬ, а не у вызывающего, чтобы вырожденный ввод нельзя было обойти.
    if (math.lengthsq(step) < 1e-12f)
        return PointCapsule(p0, padR, a, b, capsuleR);

    // ПЕРВЫЙ ВХОД ищется сканом по шагу с уточнением делением пополам: у пары
    // «отрезок против отрезка» замкнутой формы первого входа нет вовсе, а
    // ближайшее сближение отвечает на ДРУГОЙ вопрос (Ruling 191).
    // ⛔ ЧИСЛО ШАГОВ — КОНСТАНТА ФАЙЛА, А НЕ МАГИЯ: шаг снаряда 1.75 м,
    // самая узкая капсула 0.11 м ⇒ 16 проб дают 0.109 м на пробу, то есть
    // ни одна капсула не может быть пропущена целиком между пробами.
    const int Probes = 16;
    const int Refines = 12;   // 1.75 / 2^12 = 0.43 мм — вдвое тоньше допуска тестов
    float prevD = SegmentPointDistance(p0, a, b);
    if (prevD <= r) return true;                 // уже внутри в начале шага: t = 0
    for (int i = 1; i <= Probes; i++)
    {
        float ti = (float)i / Probes;
        float3 pi = p0 + step * ti;
        float d = SegmentPointDistance(pi, a, b);
        if (d <= r)
        {
            // Вход лежит в (ti - 1/Probes, ti]; уточняем делением пополам.
            float lo = (float)(i - 1) / Probes, hi = ti;
            for (int k = 0; k < Refines; k++)
            {
                float mid = 0.5f * (lo + hi);
                if (SegmentPointDistance(p0 + step * mid, a, b) <= r) hi = mid; else lo = mid;
            }
            // ⛔ ПРАВЫЙ КОНЕЦ ПОЛУИНТЕРВАЛА: контакт ровно в конце шага —
            // промах, конвенция SegmentStadium/SweepArena (тест 16).
            if (hi >= 1f) return false;
            t = hi;
            return true;
        }
        prevD = d;
    }
    return false;
}

/// Расстояние от точки до ОТРЕЗКА кости — через единственный дом клампа.
static float SegmentPointDistance(float3 p, float3 a, float3 b)
    => math.distance(p, ClosestPointOnSegment3(p, a, b, out _));

public static bool PointCapsule(float3 p, float r, float3 a, float3 b, float capsuleR)
    => math.distancesq(p, ClosestPointOnSegment3(p, a, b, out _))
       <= (r + capsuleR) * (r + capsuleR);
```

      (запись 3 «Отклонений»). Спека говорит «один солвер», не называя метода. Замкнутой формы
      первого входа для пары отрезков с радиусом **не существует** (расстояние между двумя

// Simulation/Core/PoseTable.cs — НОВЫЙ ФАЙЛ.
/// Запечённые положения костей: `клип + фаза -> положение каждой кости` в
/// системе тела (app-94sk, спека §3.5, решение владельца Н50).
///
/// ⛔ ПЛОСКИЕ МАССИВЫ, А НЕ МАССИВ МАССИВОВ, и это решение: `float3[][]` дал бы
/// SimConfigHash второй уровень вложенности, которого его хелперы не знают
/// вовсе (HashFloatArray/HashItemArray/HashHitPartArray — все одноуровневые),
/// и стоил бы аллокации на каждую строку при сборке конфигурации.
///
/// ⛔ ПОВОРОТЫ НЕ ХРАНЯТСЯ (Р512): объём задан ДВУМЯ концами, наклон выводится.
/// nlerp против slerp при межкадровом зазоре 30° расходятся на 0.033° —
/// сферическая интерполяция не нужна.
[System.Serializable]
public struct PoseTable
{
    /// Сколько костей у этого архетипа. Строка таблицы — ровно столько `float3`.
    public int BoneCount;
    /// Начальная строка каждого клипа; длина — ClipCount + 1, последний элемент
    /// равен общему числу строк (тот же приём, что у CSR-разметки: длина клипа
    /// выводится вычитанием, отдельного массива длин не заводится).
    public int[] ClipFirstRow;
    /// Строки подряд: строка r, кость b лежит в Bones[r * BoneCount + b].
    public float3[] Bones;
    /// Пороги дерева смешивания нижнего слоя — пекарь читает их ИЗ КОНТРОЛЛЕРА
    /// (`BlendTree.children[i].threshold`), а не из литералов бутстрапа (Р564).
    /// ⛔ Они едут ЗДЕСЬ, потому что вес дерева считается в Ring.Simulation, а
    /// Editor/AnimatorCatalog оттуда не виден вовсе.
    public float[] BlendThresholds;
    /// Контрольная сумма ЗАГРУЖЕННЫХ БАЙТОВ (Р514). ⛔ Поле ассета — кеш, а не
    /// источник истины: сборка конфигурации считает сумму заново и сверяет.
    public ulong Checksum;
}

```csharp
public static bool Resolve(HitPart[] parts, in PoseTable table, int poseRow,
    float3 bodyOrigin, float bodyFacingSin, float bodyFacingCos,
    float3 p0, float3 p1, float projRadius,
    out HitZone zone, out float mult, out float hitHeight, out byte partId, out float t)
{
    zone = HitZone.None; mult = 1f; hitHeight = 0f; partId = 0; t = 0f;
    if (parts == null || parts.Length == 0) return false;      // тело без объёмов не поражается
    if (table.Bones == null || table.BoneCount <= 0) return false;

    int winner = -1;
    int bestRank = int.MaxValue;
    float bestT = 0f, bestHeight = 0f;
    int rowBase = poseRow * table.BoneCount;

    for (int i = 0; i < parts.Length; i++)
    {
        HitPart part = parts[i];
        // Кости этой части, повёрнутые вместе с телом и сдвинутые в его место.
        float3 a = ToWorld(table.Bones[rowBase + part.BoneA], bodyOrigin, bodyFacingSin, bodyFacingCos);
        float3 b = ToWorld(table.Bones[rowBase + part.BoneB], bodyOrigin, bodyFacingSin, bodyFacingCos);
        if (!Geometry.SegmentCapsule(p0, p1, projRadius, a, b, part.Radius, out float ti)) continue;

        // ⛔ ПРИОРИТЕТ ЗОНЫ ПЕРВЫМ, t ВТОРЫМ, PartId ТРЕТЬИМ. Порядок
        // load-bearing: капсулы НЕ соосны, и по одному t рука, лежащая на
        // оружии перед лицом, отбирала бы попадание у головы и отдавала
        // множитель 0.75 вместо 1.7.
        int rank = ZoneRank(part.Zone);
        bool better = winner < 0 || rank < bestRank
            || (rank == bestRank && ti < bestT)
            || (rank == bestRank && ti == bestT && part.PartId < parts[winner].PartId);
        if (!better) continue;

        winner = i; bestRank = rank; bestT = ti;
        // Высота контакта — точка на шаге, а не середина части: плечо момента
        // считается от РЕАЛЬНОЙ точки касания (Н61, §3.20).
        bestHeight = math.lerp(p0.y, p1.y, ti);
    }
    if (winner < 0) return false;

    zone = parts[winner].Zone; mult = parts[winner].DamageMult;
    partId = parts[winner].PartId; t = bestT; hitHeight = bestHeight;
    return true;
}

/// Голова 0, корпус 1, руки и ноги 2 — ОДНА ступень (Р505).
static int ZoneRank(HitZone z) => z == HitZone.Head ? 0 : z == HitZone.Body ? 1 : 2;

static float3 ToWorld(float3 local, float3 origin, float s, float c)
    => origin + new float3(local.x * c - local.z * s, local.y, local.x * s + local.z * c);
```

// Simulation/Combat/Impact.cs — ВТОРАЯ ПЕРЕГРУЗКА, а не замена.
/// ⭐ ТА ЖЕ ПРУЖИНА, ПОКОМПОНЕНТНО: у линейной пружины компоненты независимы,
/// поэтому это по-прежнему ОДИН дом формулы (Р544). Скалярная перегрузка
/// ОСТАЁТСЯ — её зовёт PeakTilt, чей предмет — величина, а не направление.
public static void SpringStep(ref float2 tilt, ref float2 tiltVel,
    float dampingRatio, float settleSeconds, float dt)
{
    SpringFromSettle(dampingRatio, settleSeconds, out float k, out float c);
    tiltVel += (-k * tilt - c * tiltVel) * dt;
    tilt += tiltVel * dt;
    // ⛔ СНАП — ПО ДЛИНЕ, А НЕ ПОКОМПОНЕНТНО: покомпонентный снап обнулил бы
    // одну ось, оставив другую, то есть повернул бы крен на месте. Предмет
    // снапа — «тело пришло в покой», а это свойство вектора целиком.
    if (math.length(tilt) < RestEpsilon && math.length(tiltVel) < RestEpsilon)
    {
        tilt = float2.zero;
        tiltVel = float2.zero;
    }
}

(а) тела фикстур, чья геометрия целиком определяется числами §0.1–§0.2 спеки, даны **таблицей
премисс** — вписывать координаты значило бы завести **второй дом** этих чисел; критерий приёмки —
колонка «Премисса, без которой тест — сторож»;
(б) точный текст амендментов ADR (T13) — он пишется **по свипу**, и свип может дать больше, чем
ожидается, что прямо предписано (урок 471);
(в) числа, которые владелец крутит живьём (радиусы капсул, амплитуда реакции, пороги) — они по
построению не могут быть в плане, и это записано в спеке (Р507).

**3. Согласованность типов и имён — сверена ПО КОДУ, а не по спеке.** Открыты и прочитаны лично:
`HitZones` (весь, 317 строк), `Geometry` (`:1-200`, `:835-941`), `ProjectileSystem`
(`:68-98`, `:185-470`, `:1099-1300`), `PositionHistory` (карта членов и `Fold`),

`SimConfig` (карта полей и `HitPart`), `SimConfigHash` (`:30-75`, `:320-345`), `StateHash64`
(весь), `SeparationSystem` (`:40-175`, `:355-386`), `MobAiSystem` (`:160-262`),
`SimulationWorld` (`ArenaTopologyMatches` `:826`, `ApplyConfig` `:660-700`, `ClearCombatTimers`),
`SimConfigBuilder` (`ValidateParts` и семья высот), `LongRunHarness` (весь),
`Editor/MobFootprintAudit` (`:110-120`), `Simulation.Tests.asmdef`, `TestConfigs` (фикстурные
числа), `DeterminismTests` (`:2089-2093`, `:2171-2180`), `MobAiTests` (`:744-772`),
`SimConfigHashTests` (`:620-632`), плюс четыре ADR **из ветки** и обе разведки COMBAT-001/002.
**Найдено и учтено при написании:**
- `Hero.DashSpeed` 30 против 22 — **четвёртое** расхождение источников (отклонение 1);
- `SimConfigHashTests.Bump` знает только три типа ⇒ `StrikePartId` не может быть `byte`
  (отклонение 4);
- `WorldLifecycleTests.Bump` двигает у `float2` только `.x` ⇒ нужна **своя** фикстура 23б;
- `MobAiTests.Separation_PreventsStackingSymmetrically` — **готовый образец** фикстуры 30б, и
  находка В-C4 верна лишь наполовину;
- `MobTiltIntegrator` питается **ровно одним** видом события, а жертва `ProjectileHitPlayer` на
  проводе **отсутствует принципиально** ⇒ `PlayerTiltIntegrator` питается `PlayerDamaged`;
- `AnimIds.MobClipSet` хранит **хеши**, а не строки ⇒ «семь мест» из §10 спеки — число без
  источника, и T12 говорит «седьмое и восьмое поля»;
- собственных `ScriptedImporter` в проекте **ноль**, а `.gitattributes` — **один, в корне репо**,
  и точечное правило по имени там уже есть (строка 41).

**4. Порядок фаз исполним, и одну ошибку эта проверка нашла — в самой спеке.** Проход «что
использует то, чего ещё нет» дал: `HitVolumes` в T1 требует координат костей, которых до T4 нет

T4; мутации M331 и M363 в T2 неотличимы от оригинала. Все четыре исправлены переразрезом.

**5. Гранулярность.** Двадцать один таск; таск — один тестируемый деливерабл со своим
RED → verify FAIL → GREEN → verify PASS → мутация/гейт → приёмка → коммит. ⚠ Самые тяжёлые —
**T2** (14 шагов) и **T4** (10 шагов): первый неделим, потому что переопределение `HitPart`
ломает компиляцию **26 файлов** разом и половинчатая миграция не собирается вовсе; второй — потому

## ⭐ Вопросы владельцу (решения, которые план не принимает сам)

⚠ **Первый — блокирующий для T10b**, остальные четыре можно решить по ходу, но лучше до начала:
они меняют состав работы, а не только числа.

### 1. ⛔⛔ Дэш, слайд и даже простое столкновение будут ронять всё, чего касается сборщик

**Что обнаружилось.** Поправка Н61 сняла зонное правило: опрокидывание **вычисляется**. Спека
проверила это на пулевом пути и написала, что кламп `ImpactSpeedCap = 6` «не достигается ни разу»
(Δv чейзера от пули — 1.517 м/с). Для пули это верно. Но тот же заход даёт угловой импульс
**дэшу, слайду и столкновению**, а у них расталкивание считает **другая** формула
(`Impact.ResolveBodyPush`), и у неё **потолка нет по решению** — в коде написано дословно:
«NO CEILING HERE, AND THAT IS THE DECISION (ruling 114)».

**Числа — пересчитаны лично интегратором пружины, порог падения 51.566°:**

| Источник | Δv цели (чейзер) | Крен: ноги | корпус | голова |
|---|---|---|---|---|
| Пуля сборщика (как сегодня) | 1.52 м/с | 31.9° | 14.4° | **54.3° ↓** |
| **Слайд** (13.5 м/с) | 7.71 м/с | **162.5° ↓** | **73.4° ↓** | — |
| **Дэш, фикстурный** (22 м/с) | 12.57 м/с | **264.7° ↓** | **119.7° ↓** | **449.7° ↓** |
| ⛔ **Дэш, ИГРОВОЙ** (`HeroConfig.asset` — **30 м/с**) | 17.14 м/с | **361.0° ↓** | **163.2° ↓** | **613.2° ↓** |
| **Простое столкновение на бегу** (7.5 м/с) | 4.29 м/с | **90.3° ↓** | 40.8° | — |

⚠ Кламп по глубине проникновения (`BodySeparation.cs:123`) здесь **не спасает**: на первом тике
контакта он равен самой скорости — это записано в его же доке («on the tick a contact begins the
two agree»). И ⛔ **игровой `DashSpeed` — 30, а не 22**: это четвёртое расхождение двух источников,
которого спека не знала.

⇒ **После T10b сборщик, пробежавший сквозь толпу, положит её целиком.** Это прямое следствие Н61
(«это надо считать»), а не дефект — но масштаб надо увидеть до кода.

| # | Вариант | Плюсы | Минусы |
|---|---|---|---|
| **а** ⭐ | **Оставить как есть — физика так физика.** Дэш и слайд валят всё; смотрим на вехе | Н61 исполняется буквально и до конца; дэш сквозь толпу становится **тактикой**, а не проездом; ноль новых чисел и правил | толпа ложится **вся**, и это может читаться как сломанная сложность: волна перестаёт давить, пока сборщик крутит дэши. ⚠ И `DownedSeconds` 1.2 с × толпа = окно, которого в балансе не было |
| **б** | **Применить к расталкиванию тот же кламп `ImpactSpeedCap`, что к пуле** (только к **угловой** половине, линейный толчок не трогать) | одно число, уже существующее; дэш остаётся сильнее пули, но конечен: ноги чейзера **126°** вместо 361° — всё равно роняет, но «просека» перестаёт быть автоматической | кламп становится потолком для механики, для которой он не заводился (ruling 114 назвал причины, по которым его там нет); тяжёлые тела (элита, Директор) перестанут валиться от дэша вовсе |
| **в** | **Завести отдельное число `ShoveTiltGain`** на архетип и настроить его на вехе | самый управляемый вариант: владелец крутит «насколько таран валит» отдельно от «насколько валит пуля» | +1 балансное число и +1 двигатель хеша; настраивать вслепую нельзя — только на вехе, то есть вопрос всё равно вернётся |

⭐ **Рекомендация — «а», и причина фактическая, а не осторожность:** дэш **должен** валить — это
буквально то, что Н61 называет физикой, а `DownedSeconds` уже ограничивает эффект во времени.
Вариант «б» стоит одной строки и **обратим** на вехе; вариант «в» — мёртвое число до вехи. ⛔ Но
решение твоё: цена ошибки здесь — целая волна, лежащая на полу.

### 2. Пункт вехи 13 («тяжёлый лом делает просеку») проверяется не так, как записано

**Что обнаружилось.** Спека обещает, что снаряд массой **9.3** одновременно **роняет** чейзера
попаданием в корпус и **прошивает** его. Первая половина верна (пересчитано: 9.29). Вторая —
нет: `Impact.Pierces` требует **И** отношения масс, **И СТРОГОГО ОВЕРКИЛЛА** урона
(`damageDealt > targetHp`), и дока говорит это прописью. ⇒ по **полнокровному** чейзеру (30 HP)
лом не прошьёт ничего; просека получится только по **добиваемым** телам.

| # | Вариант | Плюсы | Минусы |
|---|---|---|---|
| **а** ⭐ | **Переписать пункт вехи: просека проверяется на добиваемых телах** | честно и ничего не стоит; правило пробития остаётся тем, что уже принято и пришпилено тестом `ExactlyLethalRound_DoesNotPierce_ButOnePointOfOverkillDoes` | «просека» окажется скромнее, чем звучала фраза «целые просеки в толпе врагов» |
| **б** | **Снять второе условие пробития** — пробивать по одной массе | фраза Н61 исполняется буквально | это **отмена принятого правила** (Ruling 102) и балансный сдвиг, которого никто не мерил; тяжёлое оружие прошивало бы всё подряд на полном здоровье |

⭐ **Рекомендация — «а».** Это пункт **вехи**, а не механики: он про то, **чем** мы проверяем, а
не про то, **что** игра делает.

### 3. Четыре числа перестанут крутиться живьём на стенде

`SpeedDampTime`, `VisualTurnDegPerSec`, `IdleAimTurnDegPerSec` и `MobTurnDegPerSec` переезжают из
`GameFeelConfig` (крутится в PlayMode мгновенно) в `HeroSimConfig`/`MobSimConfig` (баланс, входит
в `SimConfigHash`). Это **обязательное** следствие Н51: поза ведётся симуляцией, а вес дерева и
курс — часть позы. ⚠ **Но цена реальная:** «доворот стал ватным» на вехе больше не правится
ползунком — только пересборкой пары «клиент+сервер».
⇒ **Вопроса о том, делать ли, нет** (без переезда поза недетерминирована). Вопрос в том,
**заводить ли отладочный оверрайд** на время вехи:

| # | Вариант | Плюсы | Минусы |
|---|---|---|---|
| **а** ⭐ | **Не заводить.** Крутить через пересборку | ноль лишнего кода; `SimConfigHash` остаётся единственной правдой | каждая итерация доворота — сборка клиента (40–45 с) **и** сервера, плюс доставка образа |
| **б** | **Завести дев-оверрайд** (ключ командной строки, только в `Development`-сборке) | итерация мгновенная | клиент и сервер разойдутся по `SimConfigHash` — то есть оверрайд обязан ехать **на обе стороны**, а это новая проводка ради вехи |

### 4. Playables ломают половину `AnimIds` — переводить или оставить гибрид

проходящий через `Avatar`, и им же пользуется пекарь — путь в редакторе и в игре становится одним.
⚠ **Цена:** перестают работать `AnimIds.OneShotFinished`, хеши состояний и гейты наличия

| # | Вариант | Плюсы | Минусы |
|---|---|---|---|
| **а** ⭐ | **Гибрид: позу ведут Playables, одноразовые клипы (смерть, труп) остаются на `Animator`** | минимальная правка: `CorpseView` и его контракт «доиграть смерть и выключить контроллер» не трогаются вовсе | два механизма в одной кукле; граница между ними придётся описать в доке — иначе следующий читатель сведёт их обратно |
