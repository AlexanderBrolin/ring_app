# Ручной деплой game-сервера «Кольца»

Протокол Этапа 2 (`app-u0l`, задача Т52 плана Ф10). CI до MVP нет — образ
собирается и доставляется руками, и этот документ описывает ровно те команды,
которые выполнялись на живом хосте, а не желаемый порядок; исключения помечены
в тексте явно.

**Что где живёт.** Рабочая машина собирает образ (`client/docker/build.sh`).
Хост его получает и запускает (`docker-compose.yml` + `match.json` из того же
каталога). Клиенты идут по UDP напрямую — сервер-дискавери в проекте нет.

**Протокол идемпотентен:** каждый шаг можно повторить, и состояние от этого не
портится. Установка плагина перезаписывает свой файл, `scp` — свои, доставка
образа заменяет тег, `docker compose up -d` пересоздаёт контейнер, замер §5
сносит свой прошлый контейнер перед запуском. Шага «сначала всё почистить»
нет намеренно: `rm -rf` по пути из переменной — классический способ потерять
чужой каталог.

**Секретов в этом файле нет и быть не должно:** адреса и токены ниже —
плейсхолдеры вида `<хост>`, `<порт>`, `<токен>`. Учётные данные реестра живут
только в docker credential store рабочей машины.

## 1. Требования к хосту

| | минимум | проверено на |
|---|---|---|
| ОС | Debian 12 (bookworm) | Debian 12, x86_64 |
| CPU | 1 vCPU | 1 vCPU — матча на троих хватает с запасом (§5) |
| ОЗУ | 512 МБ свободных | 1.9 ГиБ всего, контейнер занял 125 МиБ |
| Диск | 1 ГБ | образ 174 МБ |
| Docker | Engine 20.10+ | 20.10.24 (пакет Debian) |
| Compose | **плагин v2** | ставится отдельно, см. §2 |

**Порты.** Игровой трафик — **UDP**, один порт на контейнер, диапазон этапа
`7770–7799` (по умолчанию `7777`). Мета Этапа 5 пойдёт по TCP 443 за уже
имеющимся nginx — на Этапе 2 не нужна.

## 2. Подготовка хоста (один раз)

Debian ставит `docker-compose` v1, а он **не понимает `pull_policy`** из нашего
compose-файла. Ставим плагин v2, не трогая уже установленный движок:

```bash
sudo mkdir -p /usr/local/lib/docker/cli-plugins
sudo curl -fsSL -o /usr/local/lib/docker/cli-plugins/docker-compose \
  https://github.com/docker/compose/releases/download/<версия>/docker-compose-linux-x86_64
sudo chmod 0755 /usr/local/lib/docker/cli-plugins/docker-compose
docker compose version        # должен ответить v2 или новее
```

`<версия>` — тег релиза вида `v5.4.0` (именно он проверен живьём 2026-08-16);
актуальный список — на странице релизов `docker/compose`.

Каталог развёртывания и права:

```bash
sudo mkdir -p /opt/ring && sudo chown "$USER:$(id -gn)" /opt/ring
```

Если хост уже несёт другие службы (у нас — nginx и чужие контейнеры), проверить,
что игровой порт свободен, **прежде** чем запускать (шаблон точный: `grep 7777`
поймал бы и `17777`):

```bash
ss -lnu 'sport = :7777' | grep -q 7777 && echo "ЗАНЯТ" || echo "свободен"
```

**Файрвол.** Игровой порт должен быть открыт снаружи по UDP; на хосте
развёртывания 2026-08-16 отдельного файрвола не было вовсе (`ufw`/`firewalld`
отсутствуют, `iptables -S INPUT` = `-P INPUT ACCEPT`), поэтому шага не
потребовалось. На хосте с файрволом открывается диапазон этапа:

```bash
sudo ufw allow 7770:7799/udp    # игровые серверы, порт на контейнер
sudo ufw allow 443/tcp          # мета Этапа 5 за nginx; на Этапе 2 не нужна
```

## 3. Сборка и доставка образа

Собирает **всегда рабочая машина**, с чистого дерева — тег назовёт коммит:

```bash
cd "$APP_REPO" && client/docker/build.sh            # собрать и опубликовать
cd "$APP_REPO" && client/docker/build.sh --no-push  # только собрать локально
```

`--no-push` нужен, когда реестр недоступен или образ поедет по §3.2: без флага
скрипт дойдёт до `docker push` и умрёт на нём.

⚠ **Первая сборка на новой машине ходит в сеть за фронтендом.** `Dockerfile`
объявляет `# syntax=docker/dockerfile:1`, и BuildKit тянет этот образ-фронтенд
из реестра. Фронтенд перепроверяется каждой сборкой, и локальный кэш гарантией
не является (так сказано в шапке самого `Dockerfile`): машина без сети может не
собрать вовсе. Нужен локальный фронтенд — `--build-arg BUILDKIT_SYNTAX=<ссылка>`.
**Хоста это не касается** — он образ только получает и запускает.

Дальше — один из двух путей доставки; выбор зависит от того, есть ли на хосте
учётные данные реестра.

### 3.1. Через реестр (штатный путь по спеке §3.13, решение С21)

```bash
# на хосте, один раз:
docker login
docker pull <репозиторий>/ring-server:dev
```

⚠ **Живьём этот путь не прогонялся.** Развёртывание 2026-08-16 шло по §3.2:
учётные данные реестра на хост сознательно не заносились. Пометка стоит здесь
именно потому, что остальной документ описывает исполненные шаги, и смешивать
исполненное с ожидаемым нельзя. Расхождение с формулировкой Т52 плана
(«`docker login` → `docker pull`» как канон) записано в корзину errata Ф10.

### 3.2. Прямым переносом по SSH (исполненный путь)

Учётные данные при этом на хост не попадают вовсе — образ едет по ssh-каналу:

```bash
docker save <репозиторий>/ring-server:dev | gzip -1 \
  | ssh -p <порт> <пользователь>@<хост> 'gunzip | docker load'
```

⚠ При этом пути на хосте нужен `docker-compose.override.yml` рядом с основным:
иначе `pull_policy: always` базового файла будет пытаться (и не сможет) сходить
в приватный реестр. В репозитории этого файла нет — он свойство конкретного
хоста, и создаётся на месте:

```bash
ssh -p <порт> <пользователь>@<хост> "cat > /opt/ring/docker-compose.override.yml <<'EOF'
services:
  ring-server:
    pull_policy: never
EOF"
```

После `docker login` на хосте этот файл **удаляется** — движущийся тег `dev`
снова начнёт обновляться сам, а это и есть поведение, которого мы хотим.

### 3.3. Проверка, что приехал нужный образ

Тег `dev` движется, поэтому доверять надо не ему, а метке коммита:

```bash
docker image inspect --format '{{index .Config.Labels "org.opencontainers.image.revision"}}' \
  <репозиторий>/ring-server:dev
docker image inspect --format '{{.RepoDigests}}' <репозиторий>/ring-server:dev
```

Первая команда печатает полный sha коммита, из которого собран артефакт, — это
и есть надёжная привязка образа к коду. Вторая печатает digest реестра; при
доставке по §3.2 она печатает **`[]`**, и это нормальный признак образа,
пришедшего без реестра. Форма `{{index .RepoDigests 0}}` для такого образа не
годится: она падает с `slice index out of range`.

⚠ **Тег `dev` НЕ означает `DEVELOPMENT_BUILD`.** Это «ветка доставки»: образ
всегда собирается из **релизной** цели `BuildLinuxServer`, где всё под
`#if UNITY_EDITOR || DEVELOPMENT_BUILD` вырезано препроцессором. Значит в
контейнере **нет ни симулятора задержки, ни ключа `-ring-latency`, ни
дев-оверлея** — под лагом такой сервер не проверить, и числа вехи В2 берутся с
клиентов.

## 4. Запуск

Из репозитория едут два файла — `client/docker/docker-compose.yml` и
`client/docker/match.json`; третий, `docker-compose.override.yml`, создаётся на
хосте по §3.2 и только для ssh-пути.

```bash
scp -P <порт> client/docker/docker-compose.yml client/docker/match.json \
  <пользователь>@<хост>:/opt/ring/
ssh -p <порт> <пользователь>@<хост> 'cd /opt/ring && docker compose up -d'
ssh -p <порт> <пользователь>@<хост> 'cd /opt/ring && docker compose logs -f'
```

Две ручки, не требующие правки самого файла: **`RING_IMAGE`** — образ целиком
(сюда подставляется `<репозиторий>/ring-server@sha256:<digest>`, когда нужен
воспроизводимый пин вместо движущегося тега) и **`RING_PORT`** — внешний порт.

Здоровый старт печатает две строки `ServerBootstrap:` (плеер Unity вокруг них
пишет ещё и свой служебный вывод). Первая в логе — одна строка, перенос ниже
типографский:

```
ServerBootstrap: listening matchId=… seed=… maxPlayers=3 port=7777
  startMode=WaitForAll countdownSeconds=0 rosterEntries=3 epoch=1
  protocolVersion=2 simConfigHash=0x… joinTimeoutSeconds=120
ServerBootstrap: server started — requestedFrameRate=45 effectiveTargetFrameRate=45 tickRate=30
```

**Ростер правится в `match.json`**, не в командной строке:

```json
{ "matchId": "lan-1", "seed": 20260816, "maxPlayers": 3, "port": 7777,
  "startMode": "waitForAll", "countdownSeconds": 0,
  "players": [ { "playerId": "p1", "joinToken": "<токен-1>" },
               { "playerId": "p2", "joinToken": "<токен-2>" },
               { "playerId": "p3", "joinToken": "<токен-3>" } ] }
```

Путь к файлу подаётся переменной `RING_MATCH_CONFIG`; она **бьёт** переменную с
телом JSON (`RING_MATCH_CONFIG_JSON`), если заданы обе. **Файл обязан быть
читаем uid 10001** — контейнер бежит от пользователя `ring`. При нечитаемом и
при отсутствующем файле сообщение ОДНО И ТО ЖЕ (`match config rejected — failed
to read RING_MATCH_CONFIG ('<путь>')`, код 2), так что проверять надо обе
причины: есть ли файл и какие у него права.

## 5. Эталонный замер (DoD п.8)

Капы ставятся явно, чтобы число значило одно и то же на любой машине. Замер —
**отдельный контейнер, не тот, что поднят по §4**: порт один, поэтому основной
сначала гасится (`docker compose down`) либо замеру даётся другой порт. ⚠ Порт
в JSON-ростере обязан совпадать с контейнерной стороной `-p`: слушает сервер
именно его, а не то, что написано слева от двоеточия.

```bash
docker rm -f ring-measure 2>/dev/null            # идемпотентность: имя занято прошлым замером
docker run -d --name ring-measure --cpus=1 --memory=1g -p <порт>:<порт>/udp \
  -e RING_MATCH_CONFIG_JSON='<json ростера>' <репозиторий>/ring-server:dev

# ...подключить клиентов по §6 и дождаться match-start; числа снимать ВО ВРЕМЯ матча
docker stats --no-stream --format '{{.CPUPerc}}  {{.MemUsage}}  NET={{.NetIO}}' ring-measure

docker rm -f ring-measure                        # убрать за собой
```

⚠ Снятое до входа игроков не значит ничего: сервер ждёт джоинов и почти не
тратит CPU. Числа берутся между `match-start` и `match-end`.

Измерено на матче втроём (2026-08-16, образ `c2fc0b2`, три headless-клиента с
одной машины через интернет):

| величина | значение |
|---|---|
| CPU под `--cpus=1` | **2.9–4.2 %** |
| память | **125 МиБ** из 1 ГиБ |
| исходящий трафик контейнера | ≈ **50 КБ/с** на троих, то есть ≈ 17 КБ/с на клиента |
| тик | `tickAvgMs=0.288`, `tickMaxMs=17.142` при бюджете 33.3 мс (30 Гц) |

**«CPU расходуется тиком, а не циклом ожидания»** — это и подтверждается парой
чисел: средний тик занимает 0.29 мс из 33.3 доступных, а общий расход CPU
держится около 3 % благодаря капу кадров (`effectiveTargetFrameRate=45`).
Крутись цикл вхолостую — при том же тике мы увидели бы 100 % одного ядра.

⚠ Числа выше — **не веха В2**: клиенты были ботами с одной машины, трафик
считан со стороны контейнера, а не дев-оверлеем. Порог 40 КБ/с на клиента
проверяется на В2 (Т53) с тремя живыми игроками.

## 6. Подключение клиентов

```bash
./Ring -ring-connect <хост>:<порт> -ring-player-id <id> -ring-join-token <токен> \
       -ring-latency off -logFile <лог>
```

```bat
Ring.exe -ring-connect <хост>:<порт> -ring-player-id <id> -ring-join-token <токен> ^
         -ring-latency off -logFile <лог>
```

У каждого игрока **своя** пара `playerId`/`joinToken` из ростера. Ключ
`-ring-latency off` нужен дев-сборкам: иначе они накинут симулятор на свою
исходящую, а в контейнере симулятора нет вовсе — и замер получится
односторонним.

## 7. Отказы, которые видит оператор

Три из четырёх пойманы живьём при развёртывании 2026-08-16: `BadToken`,
`DuplicatePlayer` и `no match after 120s`. Строка `UnknownPlayer` взята из кода
и прошлых сессий — в этом развёртывании она не наблюдалась.

| строка в логе | что произошло | что делать |
|---|---|---|
| `player refused … reason=UnknownPlayer` | клиент не передал `-ring-player-id` и придумал себе `dev-XXXXXXXX` | добавить ключ |
| `player refused … reason=BadToken` | токен не совпал с ростером (у нас — опечатка раскладки: `2ring-join-token` вместо `-ring-join-token`) | сверить команду с `match.json` |
| `player refused … reason=DuplicatePlayer` | тот же `playerId` уже занял место в этом матче | **перезапустить сервер** — ждать бесполезно, см. ниже |
| `no match after 120s — connected=N/3, everySeatLive=…` | собрались не все, либо чьё-то место умерло | перезапустить и собрать всех в одном окне |

**Место, однажды занятое, не возвращается.** Слоты не отзываются: вышедший игрок
остаётся в ростере, и его повторный вход — тот же `DuplicatePlayer`. Матч с
мёртвым местом **не стартует никогда** (`everySeatLive=false` в строке выше — это
и есть диагноз), сервер досиживает окно и выходит с кодом 3. Поэтому
единственное лечение — перезапуск сервера, а не ожидание.

**Окно сбора — 120 секунд** (`NetConfig.JoinTimeoutSeconds`; это число лежит в
`NetConfig.asset` и запечено в образ — правка требует пересборки образа, а не
переменной окружения). Не собрались — сервер выходит с кодом 3, и
`restart: unless-stopped` поднимает его заново. ⚠ **Клиенты при этом сами НЕ
переподключаются**: после перезапуска сервера их надо запускать заново, и всех
троих — в одном окне.

Отдельно от этого работает сторож брошенного матча: тридцатисекундная отсрочка
(`every client disconnected … exiting in 30s unless someone returns`) начинается,
только когда отвалились **все** до единого. Пока жив хоть один — отсрочка не
запускается вовсе.

`startMode=waitForAll` означает буквально: матч не начнётся, пока не войдут ВСЕ
из ростера. Кто не пришёл — таймаут на всех.

## 8. Остановка и обновление

```bash
ssh -p <порт> <пользователь>@<хост> 'cd /opt/ring && docker compose restart'  # начать матч заново
ssh -p <порт> <пользователь>@<хост> 'cd /opt/ring && docker compose down'     # погасить
```

Обновление образа — повторить §3 и `docker compose up -d`: при штатном пути
`pull_policy: always` подтянет новый `dev` сам, при переносе по ssh — новый
`docker load` заменит образ под тем же тегом.

**Коды выхода сервера.** Их называют два места: исход доигранного матча даёт
`MatchEndPolicy.ExitCodeFor`, а всё, что случилось до матча или вместо него, —
константы `ServerBootstrap` (`ExitAbandoned = 0`, `ExitBadConfig = 2`,
`ExitNoPlayers = 3`).

| код | что случилось | как отличить в логе |
|---|---|---|
| `0` | матч доигран: все игроки мертвы | `match-end … reason=AllPlayersDead exitCode=0` |
| `0` | матч брошен — вышли все, отсрочка 30 с истекла | `every client disconnected …` и **нет** строки `match-end` |
| `2` | конфиг не прочитан или не разобран | `match config rejected …` |
| `3` | к дедлайну собрались не все (в том числе «никто») **либо чьё-то место умерло** | `no match after 120s — connected=N/M, everySeatLive=false` |
| `4` | матч упёрся в потолок длительности (`MatchMaxDurationSeconds`, 1800 с) | `match-end … reason=MaxDurationReached exitCode=4` |

Собственный исход процесса **всегда** предварён строкой
`ServerBootstrap: exiting with code N`; у остановки по `docker stop` такой
строки нет вовсе, а код при этом **0** и остановка укладывается в доли секунды
— различать эти случаи надо по логу, а не по коду.

## 9. Безопасность прогона

Аутентификация — только `joinToken` из ростера, и он идёт по UDP **открытым
текстом**; шифрования нет, ограничения частоты джоинов нет. `ProtocolVersion`
отсекает чужие клиенты, но не злонамеренные. Для теста на троих это приемлемо,
но: адрес не публиковать, порт после прогона закрывать (`docker compose down`),
токены на каждый прогон менять.
